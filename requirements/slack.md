## S-2 Summarize a Slack message into a Todo

Paste the URL of a Slack message into the Todo add field. つなぎAI fetches the whole thread of the message (`conversations.replies`, 200 messages a page, at most 20 pages, for a link to a reply as well as to the first message; a blank message is skipped except the linked one, a message a later page repeats is read once, a message's lines after the first are indented by two spaces so that nothing in a text can pass as a heading or a sender, and a later page that cannot be read ends the read there; a linked message past the page cap is read on its own, and the replies the cap or that failure left unread count as omitted, at least one unless only the linked reply was left, which was read on its own and counted by the thread's reply count), summarizes it with the Claude Code CLI (`claude -p`, the model and effort of A-2 with sonnet and medium as the default, no tools, no MCP, no settings), and opens the result as a page of the Todo screen, the draft of the Todo. While the summary is on its way, a row above the list says so (and a failed summary is a closable row with the error). A thread whose lines, with their headings, fit 10,000 characters is sent whole in one call. A thread of one message that does not fit with its heading is that message alone, cut to 10,000 characters with its heading and the note below. A longer thread is split: the first message (2,000 characters at most; none when the thread's own message was blank) and the linked message (4,000 characters at most) and the latest replies (whole messages from the newest back, 3,000 characters; a single newer message over that is cut to it) go as they are, and the rest is grouped, from the newest back and at message boundaries, into chunks of at most 10,000 characters (at most 5, the ones nearest the end of the thread; a message over that is cut to it), each summarised by its own `claude -p` call (one at a time, the newest chunk first, with the same model and effort, a fixed Japanese instruction rather than the editable body of S-3, and the key points as the answer, as for M-8). The points reach the final call, at most 3,000 characters and never so many that the input passes 10,000, under "[途中の N 件の要点]" between the first message and the linked one (at the very start when the first message sent is one of the latest replies, so that it never comes between them; what a chunk leaves of its share of the characters goes to the chunks after it); the sections are headed "[スレッドの最初のメッセージ]", "[対象のメッセージ]" (what the task is about) and "[最新の返信]" (the present state), and "[スレッドの返信]" in a thread sent whole (its replies after the linked message show the present state too). When replies were left unread (the end of the thread was not read), the last message sent is followed by one fixed indented line ("（これより新しい返信は読めていません）"), so that the last message read is not taken for the end of the thread (if the line would pass 10,000 characters, that message is cut by the excess first). Every message that is cut, whichever part it is (first, linked, latest or a chunk's), is followed by one fixed indented line ("（このメッセージは長いため、ここで切っています。続きは読めていません）") in the text sent to Claude, and the whole stays within 10,000 characters. The chunk calls together have a time budget of 180 seconds, and only one chunk call runs at a time over all summaries (a slot of the two `claude -p` slots is left for M-8): the wait for that one slot is part of the budget and a chunk that cannot get it before less than 30 seconds of the budget are left fails; no chunk starts with less than 30 seconds of the budget left, and the chunk running is cut off at it (a call never runs longer than the time limit of one call, A-2). The wait for a `claude -p` slot inside a call (60 seconds) is not part of the budget, so a chunk may end up to 60 seconds after it. A chunk that fails or is cut off is logged (never its text), stops the chunks still to run (a stalled network or a refused login would fail them all), and the summary goes on to the final call. The messages of a chunk that failed or did not run count as omitted; a failure of the final call is an error. `omitted` of the summary (the unread replies, the chunks left out and the failed ones; set by Rust only, never read from the model's answer) shows in the draft as "N 件のメッセージは要約に含まれていません" when above 0, and is not sent on to `todoist_add_from_slack`. When the linked message is cut (at 4,000 characters in a split thread, or to fit a thread of one message), `targetCut` of the summary (set by Rust only, never read from the model's answer, and not sent on to `todoist_add_from_slack` either) shows in the draft as "対象のメッセージは長いため、先頭だけを要約しました". The ID and name of every Todoist project (from the last sync) go to Claude with the thread, and it names the one that fits best (only an ID in that list is kept). The draft is a page inside the Todo screen (`#todo-draft`, a section that takes the place of the list, as the task detail does: the side menu stays, there is no dimmed layer, the list of projects beside it is inert so that no other list can be chosen under it, and the focus goes into the page; a refresh of the Todo data neither closes it nor returns to the list; it opens only while the Todo screen is shown on its list, and a summary that is ready while another draft is open, while another screen is shown, or while a task is open, waits as a row "Todo の案ができました" and opens when it can). It is shaped like a task's detail: on the left the task name and the description (a short bullet list of the key points) as fields, and beside them (280px wide) the project, the date and the labels. On the right of them, past a divider the user drags, is the pane for Claude (S-18). The Todo screen's header has the back button of the task detail at its left (`#todo-back`, `aria-label` "戻る", the same part) and the title "Todo の案". The draft's own header row has, at its left, the source workspace (`.draft-team`) and the first line of the linked message (`.draft-quote`, in a lighter color; the message link is the tooltip of both) and, at its right, "Slack で開く" (`a.draft-open`, a link to the message that the app opens in the default browser, as the Slack thread's own does), and no ✕ and no entry to the prompt of S-3. The first line is the linked message's text as plain text (S-10's conversion of Slack's markup, where a mention is the user's name, or the handle of the user group, that the Slack list and thread already hold in memory, so no call to Slack is made for it, and "@不明" when that is not known), every run of white space, line breaks included, as one space, and at most 200 characters; Rust sets it as `targetText` of the summary from the message it has already read for the summary (no new call to Slack, and never from the model's answer), and does not send it on to `todoist_add_from_slack`. The row keeps it on one line and cuts what does not fit with "…" (CSS), so the workspace and "Slack で開く" stay in view; it is drawn as text (`textContent`), and is left out when the message has no text. The project (Claude's recommendation at first, tagged "推奨" on the field and on its row in the project menu, else the current one) and the date can be edited, as can the name and the description: the date field opens the same popover as a task's detail (a text field for Todoist's natural language, and a month to pick a day from, which keeps the time typed in the field (`15:00`, `9:30`, `15時`, `15時30分`, each with 午前 or 午後 in front, alone or after a date, 今日, 明日 or 明後日; an hour of 24 or more or minutes of 60 or more, and any other form such as `15時半`, `夜8時` or `3pm`, are not read), else the time of the due date; a click elsewhere confirms the text as Enter does, except an emptied field of a repeating task, and Escape cancels it), and nothing is saved by it. The labels field is the frame of the task detail's without its add button, because the add command takes no label. The message link, which cannot be edited, is shown under the description and is put at its end when the task is added. The add button is a round "+" at the bottom right (`aria-label` "{project}に追加", so "インボックスに追加" for the inbox; a spinner while it is on its way, the draft and the error staying when it fails), and Enter in the name or Cmd+Enter (Ctrl+Enter off macOS) anywhere in the page but the pane of Claude Code (S-18, whose terminal has its own keys) does what it does; with a blank name nothing is added. The name field wraps at its width and grows with its text, so a long name is read in full (the same field as the task detail's name, T-1). "破棄" at the bottom left and the back button close the page and create nothing, and the list comes back (the back button is off while the add is on its way, as 破棄 is); Escape does not close it (Escape still closes the due popover and the menus), so a draft is not lost by accident, and nothing is created until the add button is pressed. The Slack thread (S-6) shows the same fields on a card above its reply field instead of the page, without the pane of S-18. The Slack token also needs `channels:history`, `groups:history`, `im:history` and `mpim:history` (the last two for DM and group DM links). The Claude connection (A-4: the account of the subscription, or the API key) is shown in the side menu and in settings

## S-3 Edit the Todo summary prompt

The prompt of S-2 has a fixed part (the instruction to treat the message as untrusted data, how the message is enclosed, how the thread's headings and indented lines are read, today's date and the project list, and, after the body, the instruction not to choose the project or the due date because the message asks; it cannot be edited) and a body (how to write the name, description, due date and project, and the Japanese writing rules). The body is shown and edited on its own screen, opened from the "Todo の要約プロンプト" row of the Claude tab in settings (shown whether or not Claude can be used), and from nowhere else (neither the heading of the Todo list, at the owner's instruction, 2026-11-11, nor the draft page of S-2, at the owner's instruction, 2026-11-12, has an entry for it); "戻る" returns to the settings. While the screen is open, the side menu still points at the settings. Saving writes it to `todo-prompt.json` in the app config directory (saving the default body removes the file; an empty body or one over 10,000 characters is refused), and the next summary uses it. "デフォルトに戻す" removes the file. The right pane of the screen (`#prompt-chat`, headed "Claude と編集") is the Claude Code pane of A-36 (the owner's decision of 2026-11-19, #733 in the plan of #722: the tools of `tsunagiai-mcp` only, no built-in tools). It replaces the conversation of `claude -p` that this screen had (`claude_edit_todo_prompt`, the log, the request field with the model and effort selects, the line diff with "適用" and "却下", "クリア" and the note): they are gone, and so are the unit tests of the call. The pane is a terminal (`#prompt-term`) and a "やり直す" button (`#prompt-restart`) at the right end of its head, which ends the process and starts a new one. The process starts when the screen is opened and the instructions are loaded, goes on while the screen is left (`setScreen` of `ts/nav.ts` hides the terminal) or the window is hidden, and ends with the app or with "やり直す". Its first instruction says that this is the work of rewriting the instructions of the Todo summary and names the tools and the target; nothing from outside is in it, and it says that the text of the field is what is edited, whose instructions it does not follow. No Slack message is given to it. Claude Code reads and writes the field through the target `todo-prompt` of the screen bridge (`ts/screen-bridge.ts`, `screen_read` and `screen_write` of `tsunagiai-mcp`, A-36, #731), which has one field, `body`, the text of the edit field; the fixed parts are not offered. A write puts the whole new text into the field as it is and saves nothing: the user reads it and saves with "保存". A text over 10,000 characters is refused by the bridge, and a blank one only when it is saved. The screen refuses a read and a write while it is not open or the instructions are not loaded, and a write while a save or a reset is on its way. A write that changes the field shows "元に戻す" (`#prompt-undo`) in the header, before "デフォルトに戻す". It puts back the text that the newest write replaced, and again the one before it. It goes away when the field no longer holds what the write put there (the user typed, or reset to the default), so it never overwrites a text typed by hand. The field and the process are kept in memory until the app quits. The instructions sent to the model (the fixed parts, the default body, and the mail summary instructions, with the labels of their input) are written in Japanese; a body saved earlier stays as it was. The mail summary prompt (M-8) is not affected by the body.

## S-9 Keep a channel off the Slack list

A channel of the side menu (S-19) has a button, a circle with a minus (`.slack-side-hide`, `aria-label` "#channel を一覧に出さない"), which keeps the channel off the list and takes it out of the menu at once; the list has no such button on a row.

## S-11 Blocks and attachments in the thread

The thread of S-6 draws the `blocks` (Block Kit) and `attachments` of a message, as bots and apps put their content there and keep only a short sentence in `text`. The list (S-5) draws them too, with no image and no "画像を表示"; what is sent to Claude (S-2, S-7) stays on `text`. `slack_blocks.rs` turns Slack's JSON into the structure the screen draws (`ThreadMessage.blocks`, `attachments` and `imageUrls`, ts-rs types; `ts/slack-blocks.ts` only builds the nodes, and the screen decides nothing). A message that shares another message carries an attachment with `is_msg_unfurl` true, whose `from_url` and `original_url` are the shared message's address (`unfurled_urls` in `slack_blocks.rs`, which keeps only an https address of Slack: the host is `slack.com` or ends with `.slack.com`, with no port and no user name; any other address, such as `javascript:`, a relative one or one of another host, is left out and its link is drawn as the address); a link of the message's own `text` without a label (`<address>`) to one of those addresses (a string match, after `&amp;` is undone) is drawn as a link labeled "メッセージ" (`Span.link` of `ThreadMessage.rich` and `TimelineMessage.rich`, in the thread, the history of S-20 and the list alike; `ts/slack-rich.ts` only builds the `a`; a mention of a user is the other `Span.link`, S-12) and not as the address, and pressing it opens the address in the default browser as any link does, and the address is its `title`, as a button's link has (`ts/slack-rich.ts`). An address that no attachment unfurls, a bare address, an address in a code and a message with no such attachment are drawn as before; the label does not tell a public conversation from a private one (the attachment's fields do not say, which is unconfirmed), and what is sent to Claude (S-2, S-7) stays on `text`. Texts go through `plain_text` (mrkdwn, S-10's emoji, `label (URL)`; a `plain_text` object is not mrkdwn: it gets `&amp; &lt; &gt;` undone and emoji only when it says `emoji`), are put into the page as text, and only URLs are links (`linkify`: the header, the title without a link, the author, the footer and a field's title too; a title that is a link holds none). ## S-12 Slack styles in the thread

The thread of S-6 draws the styles of Slack's mrkdwn in the text of a message: `*bold*` (`<strong>`), `_italic_` (`<em>`), `~strike~` (`<s>`), `` `code` `` (`<code>`), a block between ``` marks (`<pre><code>`, scrolling sideways on a long line) and lines that start with `&gt;` (`<blockquote>`). A row of the list (S-5) draws them too (`TimelineMessage.rich`, by the same functions); what is sent to Claude (S-2, S-7) stays on plain text. The screen of the thread draws `ThreadMessage.rich`; `ThreadMessage.text` stays as a string that is not read for styles. `slack_mrkdwn.rs` reads the raw text of Slack (not the output of `plain_text`, in which the range of a `<…>` and a `&gt;` are lost) into `ThreadMessage.rich` (`RichBlock`: `paragraph` and `quote` hold `Span`s with `bold`, `italic`, `strike` and `code`, `code` holds a text; ts-rs types), and `ts/slack-rich.ts` only builds the nodes (`textContent` and `linkify`, never `innerHTML`; the elements are made with the DOM API, so an HTML tag in a text stays a text). Order: the code blocks are cut out first (the line break that sets a block off from the text beside it belongs to neither; a ``` with no partner is text; a block of blanks is dropped); the rest goes by lines, a run of lines that start with `&gt;` (and one space) is one quote and the other lines one paragraph, with the line breaks kept in the text and drawn by `white-space: pre-wrap`; in a line, an inline code (closed on the line, not empty), a `<…>` token and a web address are indivisible, and the marks are read around them. A mark works as Slack's does, at the edge of a word and on one line: it opens when it is at the start of the line or after white space or any character but an ASCII letter or digit and the next character is not white space, and it closes at the nearest mark of its kind that follows a non-space and is followed by the end, white space or any character but an ASCII letter or digit, so `snake_case` and `2*3*4` are not styled, a mark with no partner is text, and styles nest (`*_x_*`). A Japanese letter beside a mark does not stop it (not checked against Slack, which the owner cannot compare with; the sample messages are Japanese). A mark at the end of a web address (and the punctuation after it) is not part of the address (`*https://a.example*` is a bold link), and a mark inside one is text. The text of every piece goes through the same functions as `plain_text` (`unescape`, `emojify` of S-10, `token_text`), so the names of the mentions, the links and the emoji are as before. **A link with a label is its label as a link**: a `<address|label>` whose address is an http or https one (`http_url` of `slack_blocks.rs`, the same check as a button's `url`: any other scheme, such as `javascript:`, and the app's own origin stay as `token_text` reads them, `label (URL)` when the label is not the address) is drawn as the label alone, in `Span`s whose `link` is the address, with no "(URL)" after it (a title that Sentry sends, `<{URL}|*Error*>`, is the bold link Error). The label is read for the marks by the rules above as a line of its own, so a mark inside it does not reach out of it and a mark outside it can take the whole link (`*<url|l>*` and `<url|*l*>` are both a bold link); its entities and emoji are read as in any text. A `<address>` with no label, an empty label, a mention, a channel and `<!here>` are as before, and so is a link inside a code. What is sent to Claude (S-2, S-7) keeps `label (URL)` (`plain_text`, and `rich_plain` for the blocks and attachments, which adds the address after the label of a link that is not a mention of a user or a link to an unfurled message). **A mention of a user is a link** (issue #594): `<@U…>` and `<@U…|name>` are drawn as the name (`@name`, as before) in a `Span` whose `link` is the user's profile in the message's workspace, `{workspace}team/{user ID}` (`user_link` in `slack_mrkdwn.rs`), with the styles around it kept (`*<@U1>*` is a bold link); the screen draws it as any `Span.link` (S-11: an `a` with the address as its `title`, `ts/slack-rich.ts`), and pressing it opens the address in the default browser as any link does. Rust makes the address and nothing of the message's text gets into it unchecked: the ID must be `U` or `W` followed by capital ASCII letters and digits, and the workspace's address is `auth.test`'s `url` of the connected workspace as `https://{host}/` only when it is https, with no port and no user name, on a host that ends with `.slack.com` (`workspace_base` in `slack.rs`); a mention with an ID of another shape, or in a workspace whose address is not such a one, stays text. It is a link wherever a mrkdwn text is read (the list of "Which texts are read" below) and for a `user` element of a `rich_text` block that is drawn (S-11; a `rich_text` block is one paragraph of text with no style, cut only by these links), in the thread, the history of S-20 and the list (S-5, its unread replies of S-14 too) alike. A mention of a user group (`<!subteam^S…>`, a `usergroup` element) stays text: Slack's documentation gives no web address that opens a user group (its deep-linking page lists only `slack://` addresses and `app_redirect`, and "Formatting message text" says only that a group's ID is in the URL shown when its profile is viewed, without giving that URL; read 2026-11-14), and no address is guessed. `<!here>`, `<!channel>`, `<!everyone>` and a channel (`<#C…>`) stay text too. The address `{workspace}team/{user ID}` itself is not in that documentation either and was not opened on a real workspace by this code (at the owner's instruction, 2026-11-14). What is sent to Claude (S-2, S-7) and the post (S-21, S-28) are not changed. Inside a code (inline or block, and a `rich_text_preformatted`) no mark and no emoji is read and a mention is text; `&lt; &gt; &amp;` are undone and a `<…>` is read by `token_text` as in `plain_text`. A `linkify` link is made in every style but not in a code. Which texts are read: the `text` of a message (not when it was posted with `mrkdwn: false`), the `mrkdwn` objects of a section (text and fields) and of a context, and, in an attachment, `pretext`, `text` and the `value` of the fields only when `mrkdwn_in` names `text`, `pretext` or `fields` (Slack's rule). The texts of type `plain_text`, the header, the buttons, the title, footer and author of an attachment, the `rich_text` blocks (flattened, with their quote mark as text; only a `user` element of one is a link, as above) and the `markdown` block are not read, and their marks stay. `>>>` (a quote to the end of the message; a line that starts with it is text) and the contents of an attached `.md` file are not read. The blank and spacing of the text are as before. The colors are the variables of `:root` (`--code`, `--code-line`, `--chip-line`)

## S-13 Watch threads and the header of the Slack list

Under a header fixed above the list (the tint of the thread header `#st-head`; `#slack-header`), the list has two sections, "未読" (S-8) and "ウォッチ", shown one at a time: the side menu (S-19) chooses which, and the list has no tab. The header has the title "Slack" at the left and, at the right, an `.icon-btn` (`aria-label` "一覧に出さないチャンネル", with the circle with a minus of `MINUS_CIRCLE_SVG` in `ts/icons.ts`, the icon of the hide button of S-19 and not an eye, #449) that opens the Slack tab of settings. A section with no row is not drawn. **Watch**: the unit is the thread (`threadTs ?? ts`) and the row shows the thread's own message. A row shows, while it is hovered or has the focus, a bookmark button (`.feed-watch`, `aria-label` "ウォッチする") that watches its thread (`slack_watch`: it reads the thread once with `conversations.replies` and starts the count of new replies at its newest reply, so the replies that exist are not new; with `seenTs` nothing is asked of Slack and the thread is put back as it was). The messages of a watched thread (the thread's own message, and a reply also sent to the channel) are listed in the watch section only, never in the unread section, and the thread's unread messages still count in S-8's `unreadTotal` (that number is not changed). The screen moves the row at once and reads the list again from Rust's cache (`cached: true`); on a failed save it shows the error and brings the row back the same way, and the requests go through the same guard as S-9 (the latest request only, none answered while a save is on its way). A watched row has its bookmark always shown (filled, `aria-label` "ウォッチを外す"); pressing the bookmark lets the thread go (`slack_unwatch`, which answers the `seen_ts` it had and moves the position of S-14 to it) and the notice "ウォッチを外しました" with "元に戻す" puts it back with `slack_watch` and that `seenTs`. A watched row is bold when its message is unread (the position of its channel, as S-8, and the `last_read` of a channel the cache holds no message of is not known, so it is not unread). The section is ordered by the newest activity (the thread's own `ts` or its latest reply) first. A watched thread stays until it is let go, also when its channel is kept off the list (S-9); removing the workspace removes its threads. **New replies**: a row shows "新しい返信 N 件" (N above 0) for the replies of others (the user's own, by the workspace's own user ID, are not counted) after `seenTs`; a thread longer than the first page (`truncated`: a cursor or `has_more`) whose newest reply (`latest_reply`) is after `seenTs` has new replies that cannot be counted (`WatchMark.uncounted`; `newReplies` is 0): the row says "新しい返信あり" without a number (a latest reply of the user's own is not told apart there). Opening a watched row clears the count at once and calls `slack_watch_seen`, and the thread detail (S-6) calls it with `latestTs`, the newest reply `slack_thread` answered (when the thread has replies, at each read of it, the reload included): it moves `seenTs` forward (`with_seen`, never back) to the later of that and the newest reply the last check found (`seen_target`), does nothing for a thread that is not watched, and asks Slack nothing. Opening a watched row also sets the channel's read position (`slack_mark_read`, with `moves_forward` and the write scopes as S-8 says) to `WatchMark.unreadTo`, the newest unread message the cache holds of the thread (its own message, or a reply also sent to the channel; `thread_unread_to`), so a reply sent to the channel is read with the thread; the badge (`unreadTotal`) is defined as before. **Data**: `slack-watched.json` in the app config directory holds `{"watched":[{"teamId","channel","ts","seenTs"}]}` (IDs and timestamps only, written through a temporary file and a rename as the other lists are; a file that cannot be read, an ID or a timestamp that is not valid counts as not there, and a `seenTs` that is not valid becomes the thread's `ts`); the text, names and icons are in memory only (`TimelineCache.watch`) and are read again after a start. There is no upper limit on the watched threads; each full read of `slack_timeline` checks at most `WATCH_BUDGET` (20) of them over all workspaces with `conversations.replies` (the first page of 200: the thread's own message, then the replies), the ones never checked first and then the ones checked longest ago (`choose_watch_checks`), `HISTORY_CONCURRENCY` calls at a time for each workspace, in the same read (no screen or timer of its own). A 429 is not retried: it ends that workspace's checks for the round and stops them until `Retry-After` has passed (`replies_limited_until`). The checks run beside the read of the read positions (`tokio::join!`), after the user's own ID of each workspace is known. `slack_watch` is stopped by the same wait (it answers an error at once while it lasts, calls `conversations.replies` without a retry, and starts the wait on a 429). A check that fails keeps what the last good one found. A thread Slack says cannot be read (`thread_not_found`, `channel_not_found`, `not_in_channel`, `message_not_found`, or an answer without the thread's own message) is kept as a row that says so (`watch.status` "unreadable": the text "このスレッドは読めません…", the row not pressable) with its bookmark, so it can be let go; a thread not checked yet (or whose checks failed so far) is "pending" ("読み込んでいます…"), and while any is pending `refreshSecs` is 60 (`REFRESH_BUSY_SECS`, `unchecked_watch_rows`), as it is while channels are unread or a thread of S-14 was never checked, and 120 otherwise (300 while every workspace is connected by Socket Mode, S-16). Only the workspaces that could be read in the round are checked. `slack_watch` takes the file lock first and then reads the workspace list again, and saves nothing (and answers `NO_WORKSPACE`) for a workspace that has been removed. `slack_watch_seen` returns at once, without the lock, for a thread the cache has no check of; the screen reads the list again from the cache (`cached: true`) after it when a read was on its way, as `slack_mark_read` does. `WatchMark {newReplies, uncounted, status, unreadTo}` is the `watch` of a `TimelineMessage` of the section (null in the unread section).

## S-14 Unread replies in the Slack list

A thread with unread replies is listed in the unread section of S-8, in the group of its channel, with its replies under its row, also when the thread's own message is read. **What is unread**: Slack's documented read state of a thread is on the parent in `conversations.replies` (`subscribed`, `last_read`); `conversations.history` does not document it, so it is read only from there, and a field that is missing gives no unread reply (not checked on a real workspace). Slack has no public API to write a thread's read position (`conversations.mark` is the channel's), so **reading a thread here does not clear it in Slack**: the position used is the later of Slack's `last_read` and the one kept here. A reply is unread when the parent says `subscribed: true` with a valid `last_read`, its `ts` is later than the position (compared as numbers), it is no reply of the user's own (with the user's own ID not known, the thread is not checked in that read) and it is no reply also sent to the channel (that is a message of the channel, S-8, listed and counted there). Watched threads (S-13) are out of this entirely: no call, no toggle and no count of it, their rows keep "新しい返信 N 件". So are the channels kept off the list (S-9) and a channel the user is no longer in. **Reading**: a full read of `slack_timeline` checks at most `THREAD_BUDGET` (20) threads over all workspaces with `conversations.replies` (the first page of 200, as S-13), `HISTORY_CONCURRENCY` calls at a time for each workspace, beside the read positions and the watched threads (`tokio::join!`). The candidates are the messages held that are the parent of a thread with `reply_count` above 0 (not a reply also sent to the channel), and the threads whose last check found unread replies, even when the parent has left the 20 messages held of its channel. The pure `choose_thread_checks` takes the ones never checked, then the ones whose reply count in `conversations.history` changed since the last check, then the ones with unread replies, then the rest, which only once `THREAD_RECHECK` (1 hour) has passed since their last check, so that threads with no activity do not use the budget in every read; within each, the ones checked longest ago. Only the workspaces that could be read in the round are checked. A 429 is not retried, ends that workspace's checks for the round, and shares `replies_limited_until` with S-13. A thread Slack says cannot be read (`unreadable_code`, or an answer without its own message) loses what was found; another failure keeps it. `refreshSecs` is 60 while a candidate was never checked, so that the first pass drains. `TimelineCache.threads` keeps, in memory only, when each thread was checked, its reply count, the parent, Slack's position, the `ts` of its unread replies and the newest `UNREPLIED_MAX` (20) of them to draw, the newest reply and whether the page was the end of the thread. An entry goes with its workspace, and when its thread is neither held nor unread. A read from the cache (`cached: true`) makes the same answer from these with no call. A thread longer than the page whose newest reply is after the position has unread replies that cannot be counted (`uncounted`, as S-13). **The position kept here**: `slack-thread-seen.json` in the app config directory holds `{"seen":[{"teamId","channel","ts","seenTs"}]}` (IDs and timestamps only, written through a temporary file and a rename as the other lists are; a file that cannot be read, or an entry with an ID or a timestamp that is not valid, counts as not there when the list is read for the screen, but a write (`save_seen_moves`) never overwrites a file that cannot be read and answers an error, as for `slack-watched.json`), because otherwise every start would bring back replies read here. It keeps the 500 with the newest `seenTs`, `seenTs` only moves forward, and removing the workspace removes its entries. `slack_thread_seen` (`teamId`, `channel`, `ts`, `latestTs`) moves it, asks Slack nothing, checks the IDs and timestamps, does nothing for a watched thread or a workspace that is gone, and writes only when the position moved; it is called when a row with unread replies is pressed (with `latestTs`, the newest unread reply) and each time `slack_thread` answers with replies (S-6, with the newest reply read), and the list is made again from the cache when it moved. Letting a thread go (S-13) moves the position to the reply it had been seen up to. **Answer**: `TimelineMessage.unreadReplies` is `{count, uncounted, share, latestTs, replies}` (null in the watch section and when there are none; `count` is 0 when `uncounted`; `share` is what the thread adds to the badge, 1 when `uncounted` else `count`, set by Rust only, and the screen sums it when it takes rows off the badge), and `TimelineReply` has `ts`, `name`, `iconUrl`, `text`, `rich`, `blocks`, `showText`, `attachments` and `hasFiles`. The unread section is sorted by the newest of the row's own unread `ts` and its unread replies, newest first, and keeps the newest 10 rows of each channel (`merge_thread_rows`; the screen draws a group oldest first, S-8); when the parent has left the messages held, the parent saved at the check draws the row. `.unread` (bold) stays the parent's own. `unreadTotal` adds the unread replies of all the threads known, not only the ones listed (a thread that cannot be counted counts 1). `UnreadChannel.threads` of S-8 lists the threads of each channel with unread replies, `ts` and the newest unread reply `latestTs`, also those whose row is past the 10 of the channel. **Screen**: under the row a toggle (`.feed-thread-toggle`, "未読の返信 N 件", "未読の返信あり" when it cannot be counted, `aria-expanded`, a chevron) opens and closes the replies and does nothing else: no read, no thread, no change of the scroll position. It starts open. A closed thread is remembered in memory per thread through the redraws and the return from a thread, and forgotten when the thread has no more unread replies. ## S-16 Update the Slack list by Socket Mode events

The owner registers an App-Level Token (`xapp-`, scope `connections:write`) for a workspace, and the app keeps a Socket Mode connection to Slack for it, so that a message posted, changed or deleted reaches the Slack list (S-5, S-8, S-13, S-14) and the Slack button's badge within about a second, instead of at the next read. The reads of the list stay: they bring the channels and threads no event names, and what an event cannot carry.

**Registering.** The Slack tab of the settings has a card "リアルタイム更新" (after the card of S-9; its header has the `?` hint, `#slack-socket-help`), with a row per workspace (avatar, name, a line, the state label with its dot, and when a token is registered an `.icon-btn` "{workspace} の App-Level Token を削除" that asks first, as the unlink of a workspace does), and an add row: a select of the workspaces (`#slack-socket-team`), a password field (`#slack-socket-token`, "App-Level Token（xapp-…）") and "登録". `slack_app_token_set(teamId, token)` trims the token and refuses one that is not `xapp-` followed by letters, digits and hyphens ("App-Level Token は xapp- で始まります"), or for a workspace that is not connected; it accepts the token only when Slack answers `apps.connections.open` with it (a refusal is shown as the other Slack errors are), keeps it in the OS keychain (service `jp.mysis.tsunagiai.slack-app`, user name the workspace's `team_id`, a value never shown, logged or returned), and starts the connection. The field is emptied as soon as it is read, and an error is shown on a card (A-28). `slack_app_token_remove(teamId)` stops the connection and deletes the token. Removing a workspace (the unlink button of its row in the Slack card, `slack_remove_workspace`) does both. Both answer the connections (`SocketStatus`: `teamId` and `state`), and `slack_socket_status` answers them at any time.

**State.** The state label of a row is "未登録" (no token; gray), "接続中" (the first connection is on its way; gray), "つながっている" (Slack said hello; green) or "つなぎ直し中" (the connection ended, or could not be made, and the next try is waiting; orange). The line under the name says how often the list is read: "未登録の間は、2 分ごとに読み直します" and "つながるまでは、2 分ごとに読み直します" while not connected, and "新着をすぐに一覧へ出します。読み直しは 5 分ごとです" while connected. Rust sends each change as the event `slack-socket-status` (one `SocketStatus`), and the card follows it.

**Connection.** At startup the app connects every workspace that has a token (`slack::socket::start_all`, spawned in `setup`), and registering a token connects at once. A task per workspace calls `apps.connections.open` with the token, connects to the `wss` address of slack.com it answers (anything else is refused), and answers every envelope with `{"envelope_id": …}` whatever it carries. `hello` makes the state "つながっている". A `disconnect` with the reason `warning` is ignored; `refresh_requested` makes the connection again at once; any other reason, a close, an error, and a socket that sent no frame for 90 seconds (the app pings every 30) make it again after a wait that doubles from 1 second up to 60 (the waits start over when a connection has lasted 60 seconds after its hello, not at the hello itself, so that a connection that drops at once is not made again every second and does not start a full read every second). When Slack refuses the token (`invalid_auth`, `token_revoked` and the other codes of a dead token) the token is deleted (only if the token kept is still the one Slack refused; a token registered meanwhile stays) and the state is "未登録", with the reason logged. TLS is rustls with the system's roots.

**Events.** Only `events_api` envelopes of the workspace (`team_id` of the payload) whose event is a `message` with `channel_type` `channel` or `group`, or with no `channel_type` (the example of `message_deleted` in Slack's reference has none, and `message_changed` is treated alike), are taken, whatever the subtype (a post, a reply, `message_changed`, `message_deleted`); an event with another `channel_type` (`im`, `mpim`) and the other events are answered and ignored. Whether the channel of an event with no `channel_type` is one the user is in is decided by the channel list the app holds, as for the others (below). An event names its channel and, for a reply or a changed or deleted message of a thread, the thread (`thread_ts` of the event, or of its `message` or `previous_message`). It builds no row. The events of a channel that come within one second of the first are one read again (a channel at a time, in order; the threads they name, the newest five at most, are read together). A channel is read again by events at most once in 10 seconds, and a workspace gets at most 20 calls (`conversations.history`, and `conversations.replies` for each thread checked) in a minute for these reads, so that a busy channel cannot use up Slack's limit (about 50 a minute for each method) that the full read needs (up to 40 `conversations.history` calls); a read that is held back is not dropped: it waits, merged with the events that come meanwhile (their threads added), and is made when the gap or the minute allows. A read that would make no call (below) is dropped before the budget, and uses none of it. That read leaves alone a channel kept off the list (S-9), a channel not in the channel list the app holds, and a workspace Slack has rate-limited; it reads the channel's `conversations.history` as the list does (S-5), asks `conversations.info` for its read position only when none is held, checks the named threads with `conversations.replies` as S-13 (a watched thread) and S-14 (a thread with replies held) do, asks `users.info` for the people the new messages draw that the cache does not know, replaces what the cache holds for the channel (`SlackState`), and sends the event `slack-timeline-dirty`. The screen then calls `slack_timeline` with `cached: true` (no call to Slack) and draws it, and sets the badge (`unreadTotal`) from the answer. The rules of S-8 (unread by the channel's read position), S-9, S-13 and S-14 are those of the full read, because the same functions make the list.

**Full reads and the wait.** When a connection is made (the hello), Rust sends `slack-socket-resync` and the screen reads the list in full, as at startup; when a read or a save of S-9, S-13 or S-15 is on its way, it does so once that is done (an event is not sent again after about 6 minutes, so what came while there was no connection must be read). A full read does not overwrite a channel that an event read after the full read began (`TimelineCache::replace_history` keeps those entries of the channels in the list), so that a message posted while it goes on stays in the list and the badge. The list is also made again from the cache at each `slack-socket-status`, so that the wait follows the state. `refreshSecs` is 300 instead of 120 while every workspace is connected (`live_refresh_secs`); it stays 60 in the cases of S-5, S-13 and S-14, and it is 120 as before while any workspace is not connected. The reads on a timer are what shows a channel read on another device: the read position (`channel_marked` and `group_marked`) is an event of the RTM API only, and the Events API does not send it.

**Not in this requirement.** Direct messages and group direct messages (S-5), reactions, files and the other events, and the app's own use of Socket Mode's other payloads (slash commands, interactive components).

While the workspace is rate-limited (the full read of S-5 found it so, `TimelineCache::rate_limited`) the command answers the error "Slack の呼び出し制限のため、しばらく読めません" at once and calls nothing; a 429 of its own call stops the workspace's reads for the wait Slack asked (`TimelineCache::limit`, as the full read does) and answers the same error (`history_failure`, covered by `cargo test`).

A message is drawn as a row of a group of the unread section is (S-8): the avatar, the name, the time, the text, its reactions (S-22) under the text, ending with the button of the emoji picker (S-25), and "N 件の返信" under them when it has replies, with the bookmark of S-13 beside it, which is on when its thread is among the watched ones and watches or lets go of the thread as in S-13. A reply that was also sent to the channel (`subtype` `thread_broadcast`, with a `thread_ts` other than its own `ts`) has a line above its text, "スレッドに返信済み: {the start of the message it replied to}", muted (the color of the time) and cut with an ellipsis to one line (`.feed-thread-reply`). `slack_channel_history` gives it as `threadReply` (`ThreadReply`: `parent`), which is `null` for every other message and for every row of the unread list, which draws no such line. `parent` is the thread's own message as `headline` makes it (S-10's plain text, one line, at most 200 characters); the text is taken from the `root` that the message carries, else from the message of the same `conversations.history` answer whose `ts` is the `thread_ts`, and when neither is there (or its text is blank) `parent` is `null` and the line is "スレッドに返信済み" alone. Slack's documentation shows `root` only in the payload of the `thread_broadcast` message event (https://docs.slack.dev/reference/events/message/thread_broadcast); the pages of `conversations.history` and `conversations.replies` do not mention it, so whether the history carries it was not confirmed, and the message of the page is the fallback. `broadcast_of` (a pure function: the `root`, the page's parent, or neither) is covered by `cargo test`. The line takes no press: it lets the press through to the row.

Pressing the row or "N 件の返信" opens the thread of S-6 (`threadTs ?? ts`) in place of the history, and its back button shows the history again at the scroll position it had. The history opens at the newest message, at the bottom.

The history itself sets no read position. The press on the channel reads it (S-15), and that is the read of the history: a press on the same channel again reads the history once more and the channel again only if something is unread by then. Opening a thread from the history, or going back, reads nothing more. A thread opened from it is seen as S-6 and S-14 say of any thread. The history is read when the channel is pressed and after a post of S-21, not on a timer, and Socket Mode (S-16) does not change it; it is drawn again (not read again) when what it shows changes, such as the watched threads.

A history that cannot be read shows the error ("読み込めませんでした: …") in the body with "再読み込み", which reads it again; with messages already shown, a failed second read keeps them and shows the error above them. While the first read is on its way the body shows "読み込んでいます…".

## S-21 Post to a Slack channel

Under the history of a channel (S-20) is a rich field to post a message to that channel (`#sc-reply`, the same frame as the reply field of S-6), made by `rich-editor.ts` (the part that the reply field of S-6 takes too). It is one frame with three parts, from the top: a toolbar (`#sc-tools`, `role="toolbar"`, `aria-label` "書式"), the field (`#sc-input`, Milkdown, A-26, the editable part `.ProseMirror` with `aria-label` "チャンネルに投稿", three lines high and growing to six, with no placeholder and no line of text that explains it), and a row under it with the round send arrow (`#sc-send`, `aria-label` "投稿", at the right end of the row, inside the frame). There is no text button "投稿する".

The toolbar has nine buttons in three groups, each an icon button with its `aria-label`: bold ("太字"), italic ("斜体"), strike ("取り消し線") | link ("リンク"), numbered list ("番号付きリスト"), bulleted list ("箇条書き") | quote ("引用"), code ("コード"), code block ("コードブロック"). A button acts on the selection of the field, takes no focus from it, and gives the focus back to the text. The link button shows a one-line field (`aria-label` "リンクの URL") in the toolbar: Enter makes the selection a link to that address and closes it, Escape closes it. Milkdown is read the first time the channel screen is shown (`vendor-load.ts`); until it is there the toolbar, the field and the arrow are off, and a read that fails shows "エディターを読み込めませんでした: …" above the frame. Enter is a line break (a new paragraph, or a new item in a list), and Cmd+Enter (Ctrl+Enter off macOS) posts, unless it only confirms an IME conversion, as in S-6. The arrow is off while the text is blank (spaces and line breaks alone).

The post is `slack_channel_post` (`teamId`, `channel`, `text`, and an optional `markdown`), which posts the text as it is (`*` stays markup) when `markdown` is false or missing, with `chat.postMessage` under the user's own name, through the same Rust function as S-6 (`send_post`: the scope `chat:write`, `unfurl_links` and `unfurl_media` off, the same Japanese errors), so that no new Slack method and no new scope is used. Rust checks that `teamId` is the ID of a connected workspace, that `channel` has the form of a channel ID and is one the workspace's channel list holds (the list the side menu is made of, as `slack_channel_history` checks it), and, in `post_text`, that the text is not blank and not past 10,000 characters (`POST_LIMIT`); nothing is sent otherwise. It is no thread reply. The text goes to Slack only on the user's press or key.

When `markdown` is true (`slack_channel_post` and `slack_reply`, S-6), the text is Markdown and `slack_markdown.rs` (`to_mrkdwn`, a pure function) turns it into Slack's mrkdwn before the checks of `post_text`. It handles nine forms: bold (`*x*`), italic (`_x_`), strike (`~x~`), a link (`<url|text>`), a numbered list, a bulleted list, a quote (`> `), inline code and a code block (the language of a block is dropped); a heading becomes a bold line, and an empty paragraph of the editor (`<br />` alone in its block, what Enter pressed twice leaves) is one more blank line, not the text of a tag; anything else (a table, HTML) stays as escaped text. `&`, `<` and `>` are escaped as `&amp;`, `&lt;` and `&gt;`, and nothing else is. Only an address with the scheme `http`, `https` or `mailto` becomes a link: any other, including one that starts with `!`, `@` or `#`, is dropped and the text alone stays, so that no Markdown link makes Slack notify `@channel` or a person. The limit of 10,000 characters is counted on the converted text, and so is the blank check. The channel field passes `markdown` true, with the Markdown that the field exports as `text` (it ends with a line end).

While the post is on its way, the field and the toolbar of that channel are off, and the arrow of every channel stays off until it ends, so that a text is never posted twice. On success the field is empty and the history is read again (S-20's `slack_channel_history`) and scrolled to its newest message, where the message just posted shows; no read position is set. On a failure the error ("投稿できませんでした: …", from Rust) shows above the field and the text stays; typing or choosing another channel hides it. When the post ends after the history was left (another channel or a section chosen, or a thread shown), a toast tells the result instead ("#channel に投稿しました", "#channel に投稿できませんでした: …"), and a text that failed stays.

What is written is kept for each channel (`{teamId}/{channel}`), as the Markdown the field exports, in memory only, until the app quits: choosing another channel and coming back finds it, a section or a thread in between does not lose it, and it is in no file or log. Typing does not export the Markdown: the field only marks the text as changed and sets the arrow from whether it is blank, and the Markdown is taken when it is needed, which is when the channel is switched, and when the field is posted, so that no text is lost.

The unit tests (`cargo test`) cover the check of the text of a post (`post_text`, S-1) and the conversion to mrkdwn (`to_mrkdwn`). The E2E spec `slack-list.e2e.ts` covers the toolbar and the arrow (the nine buttons and the arrow with their names, no placeholder, no text button), the call and its arguments with `markdown` true (a text made bold with the toolbar is posted as Markdown `**…**`), Cmd+Enter and the arrow as ways to post, Enter as a line break, the arrow off for a blank text, the field emptied and the history read again, the error with the text kept, the field and the arrow off while the post is on its way and a second press that posts nothing, and the text kept for each channel.

## S-25 Add and take off a reaction

In the thread (S-6) and in the history of a channel (S-20) the reactions of a message (S-22) are buttons: pressing one the user did not give adds it, and pressing one the user gave takes it off. A reaction the user gave has the accent color on its frame (`.reaction.mine`) and `aria-pressed` true; the others have `aria-pressed` false. The list (S-5), the watch section (S-13) and the pane of the unread (A-35) still draw no reactions. An emoji the message does not have yet is chosen in the emoji picker, which the last button of the reactions opens.

`Reaction.mine` is true when the token's own user is among the people who gave the reaction: `thread_slim` (the thread) and the history's rows keep `users` of each reaction, and the rows of the list, which its timers keep, do not (`list_slim`: up to 100 people for each reaction would be held for nothing), `reactions_of` takes the user from `own_user_id` (`auth.test`, asked once for a workspace and kept in `TimelineCache`; `slack_thread` and `slack_channel_history` ask for it only when a message they read has a reaction), and `mine` is whether that user is in `users`. A reaction with no `users`, a `users` that is not a list, and a user that is not known (`auth.test` failed) give `false`. Slack lists up to 100 people for a reaction, so on a reaction given by more people `mine` can be false when the user did give it; the press then adds it, Slack answers `already_reacted` and the frame turns to mine. `users` is used for `mine` only: it is in neither `ThreadMessage` nor `TimelineMessage`, nor shown.

The command `slack_react` (`teamId`, `channel`, `ts`, `name`, `add`) adds (`reactions.add`) or takes off (`reactions.remove`) the user's reaction `name` on the message `ts` of `channel`, with the workspace's own token and the arguments `channel`, `timestamp` and `name`. It is called only by a press. Before anything is sent Rust checks that the workspace is a connected one (`token_key` and the workspace list), that `channel` has the form of a conversation ID (`valid_channel`) and `ts` of a message time (`valid_ts`), and that `name` is a reaction name (`valid_reaction_name`); the thread may be in a DM or a group DM, so the channel list is not consulted. Anything else is refused with `貼り付け先が不正です` and nothing is sent. A reaction name is the emoji's own name, 1 to 100 characters, each a letter or digit of any script (a custom emoji may be named in Japanese, as `ステキ`), `_`, `-`, `+` or `'`, never upper case, with no space, colon or control, zero-width or bidirectional character; it may be followed by `::skin-tone-2` to `::skin-tone-6`, as `+1::skin-tone-2`. Slack's documentation gives no list of the characters of an emoji name, so this is the set of the standard names (`+1`, `t-rex`, `flag-jp`) and of the custom names seen; a name outside it is refused here, and Slack's `invalid_name` still ends a name it does not take.

`slack_react` answers true when Slack changed the reaction, and false when it was in the asked state already: `already_reacted` when adding and `no_reaction` when taking off are not failures. The other answer of the pair (`no_reaction` when adding, `already_reacted` when taking off) is a failure. A failure is logged and returned in Japanese (`react_error`): `missing_scope` says that the Slack app lacks `reactions:write` (or the scope Slack names) and that it must be added and the token pasted again; `too_many_reactions`, `too_many_emoji`, `invalid_name`, `message_not_found`, `thread_locked`, `is_archived` and `not_reactable` have a sentence of their own; the other codes are worded as every Slack error is (`error_message`). A 429 is retried as every call is. The name of a reaction and its message are not logged.

`pressReaction` in `ts/slack-view.ts` runs the press. The reaction's button is off from the press until Rust answers, and a press on the same reaction of the same message (by workspace, conversation, message and name) while one is on its way sends nothing, even on a button drawn again meanwhile. On a success the screen changes its own state and draws the reactions of that message again in place, with no read of the thread or the history: the frame follows what was asked (`mine` is the new state), the count goes up by one for an add and down by one for a take-off when Slack changed it (true), and stays when it was so already (false); a reaction whose count falls to 0 is gone, and the box is left with the button of the picker alone when it was the last. On a failure it shows the error in a toast (`リアクションを変えられませんでした: …`) and changes nothing, and the button can be pressed again. The change goes into every copy of the message the screen holds, not only the one that was pressed: a thread opened from the history of a channel (S-20) and the history behind it hold their own copies of the same message (`onReactionChange` of `ts/slack-view.ts`, taken by `ts/slack-thread.ts` and `ts/slack-channel.ts`), so the history is as the press left it when the thread is left, and a pressed message whose thread was read again meanwhile is drawn from the copy of that read. A copy that already is in the asked state (a reaction that is the user's when it was added, one that is not the user's or is gone when it was taken off: a read that Slack answered after taking the press) takes no change, so the press is never counted twice; the E2E spec `slack-thread.e2e.ts` covers an add and a take-off read meanwhile. The keyboard focus stays on the reaction after the redraw when it was there. A press takes nothing from the row it is in: in the history it does not open the thread. When the screen was drawn again while the press was on its way, the box of that message on the page is the one drawn again, from the message that box shows (the thread read again), so its count and frame are the new state; when it is not on the page, nothing is.

`reactions:write` is an optional scope: it is in `OPTIONAL_SCOPES` and in the scope list of the Slack tab of the settings (`OPTIONAL_KINDS` of `ts/permission-pane.ts`, and its sentence in the hint), and a token without it is listed as lacking it with the other optional scopes. It is not in `TIMELINE_SCOPES`, so the list does not warn of it. A token without it still shows the reactions; only a press fails, with the message above. The emoji picker (below) uses the same `slack_react` and the same update after a success.

The unit tests (`cargo test`) cover `valid_reaction_name` (standard, skin-tone and Japanese names, the limit of the length, and a space, a colon, upper case, a control or zero-width character, a bad tone), `valid_reaction_target` (a channel, a DM and a group DM, and each part of a bad form), `reactions_of` with the own user (`mine` for a user in `users`, none without `users`, with a `users` that is not a list, or without the user; `users` not in the serialized reaction; the list's copy of a message keeps no `users`, the history's does), `react_error`, and `react_at` against a local port (`reactions.add` and `reactions.remove` with their body and token, `already_reacted` and `no_reaction` as false, the other pair as a failure, `missing_scope` and `too_many_reactions`). The E2E specs `slack-thread.e2e.ts` and `slack-list.e2e.ts` cover the buttons and their frame and `aria-pressed`, the call of `slack_react` and its arguments for an add and a take-off in the thread (a DM too) and in the history, the name as given, the count and frame changing in place with no read and the thread not opening, a reaction gone at 0, an answer of false, the toast and the unchanged state on a failure, one call for presses while one is on its way, the focus, and `reactions:write` in the scope list of `settings.e2e.ts`.

The reactions of a message end with a button, `.reaction-add` (an icon of a smile with a plus and no text, `aria-label` "リアクションを追加", `aria-haspopup` "dialog"), in the box `.reactions` that `reactionsNode` of `ts/slack-view.ts` makes for every message of the thread and of the history. A message that has reactions always shows it. A message with none has the box with this button alone (`.reactions.empty`), which is laid over the top right of the message (`position: absolute`; in a row of a list, left of the bookmark `.feed-watch`, over the date, which is hidden while the box shows) and so takes no room and moves no line, and is transparent and takes no press (`opacity: 0`, `pointer-events: none`, never `visibility: hidden`, so the keyboard can still focus it) until the pointer is on the message (`.st-msg:hover`, `.feed-item:hover`), the focus is in the message or in the box (`:focus-within`, so the keyboard reaches it) or the picker opened from it is open (`aria-expanded` true). In the history the box takes no press of the row except its buttons, as the reactions do.

Pressing the button opens the picker (`openEmojiPicker` of `ts/slack-emoji-picker.ts`, a `.menu` shown by `showMenu` under the button, `role` "dialog", `aria-label` "絵文字を選ぶ"), one at a time as every menu, closed by Escape and by a press outside it (`menu.ts`), and the keyboard focus goes to its search field (`aria-label` "絵文字を検索", no placeholder). Under the field the picker lists, in this order and each under a heading, よく使う (the emoji the user reacted with most in this workspace, most first, at most 24 of the ones the list holds, from `slack_emoji_frequent`: see "The emoji used" below; the section is left out when there is none, and it takes the place of 最近, which held only the emoji added in the run), カスタム (the workspace's custom emoji with an image, S-26, by name) and 標準 (the standard emoji). A cell is the Unicode emoji, or the image of a custom emoji (a grey slot until it is fetched), with `aria-label` and `title` `:name:`. The text narrows the cells to those whose name holds it, in any case (a part of the name, trimmed; a section left with none is hidden), and Enter picks the first cell left. When none is left the picker says "該当する絵文字がありません". While the list is on its way it says "読み込んでいます…", and when it cannot be read "読み込めませんでした: …" (the next opening asks again).

The command `slack_emoji_catalog` (`teamId`) answers `EmojiCatalog`: `standard` (`name` and `emoji`) and `custom` (`name` and `image`, the address of S-26). Rust checks that `teamId` has the form of a workspace ID and is a connected one (`BAD_TARGET`, `NO_WORKSPACE`), asks `emoji.list` only when the cache of S-26 has no fresh answer and the token is not known to lack `emoji:read` (`lookup_emoji`), and builds the lists with `emoji_catalog`, a pure function. The standard emoji (`standard_emoji`, built once and kept while the app runs) are those of the `emojis` crate in its order (the Unicode groups; no skin tone variant), each once, under Slack's own name where the table of S-10 (`slack_emoji.rs`) names the emoji (`thinking_face`) and under the crate's first shortcode otherwise, then the emoji of that table the crate lacks; an emoji with no name and a name `valid_reaction_name` refuses are not listed, and an emoji is the same emoji with or without its variation selector. The custom emoji are those of `emoji.list` whose value is an address that `resolve_emoji` makes an image, by name; an `alias:` entry is not listed again (it is the same image), and a name `valid_reaction_name` refuses is left out. A standard emoji whose name a listed custom emoji has is not listed (the workspace's own takes it, as Slack draws). A token without `emoji:read` gives the standard emoji only. The names are those a reaction takes; Slack's own `invalid_name` still ends a name it does not take (the gemoji names of the crate are not all Slack's).

The screen keeps the answer for each workspace for an hour (`catalogOf` in `ts/slack-emoji-picker.ts`, in memory only), together with the grids of cells made from it (the cells are made once, and opening the picker again moves the grids and makes none), so the list is not asked for or built again each time the picker opens; a failed read is not kept, and neither is a list with no custom emoji. The lists of all workspaces are dropped when a token is pasted again or a workspace is removed (`forgetEmojiCatalogs`). Typing in the search field writes only the cells whose state changes. Choosing a cell closes the picker and calls `pressReaction` with `add` true and the emoji: `slack_react` is called as for a press (the workspace, the conversation, the message's `ts` and the cell's name), and on a success the box is drawn again in place, with no read: when the message has a reaction of that name its count goes up by one when Slack changed it (true) and stays when it was so already (false) and the frame is the user's; when it has none the reaction is added at the end, with count 1, the user's frame, `emoji` the Unicode emoji or `:name:` and `image` the custom emoji's. The add is a use (`slack_emoji_used`, below). On a failure the error shows in the toast as for a press and nothing changes. A reaction that falls to 0 leaves the box with the button alone (`.empty`).

The emoji used (#1297, #1299). ## S-26 Custom emoji in reactions as images

The thread (S-6) and the history of a channel (S-20) draw the reaction of a custom emoji as the emoji's image, not as `:name:` (S-10, S-22). The list (S-5), the watch section (S-13) and the pane of the unread (A-35) still draw no reactions. An emoji in the text of a message is not drawn as an image: it stays `:name:` as S-10 says.

Rust reads the custom emoji of a workspace with `emoji.list` (User Token Scope `emoji:read`, Tier 2): a name, and for it an image address or `alias:` and another name. The answer is kept in `TimelineCache` (`emoji`), for each workspace, in memory only, and no file holds it. It is kept for an hour (`USER_TTL`) and for five minutes when Slack could not answer (`USER_MISS_TTL`), and it goes with the workspace (`forget`). Drawing a reaction never calls `emoji.list`: `slack_thread` and `slack_channel_history` ask for it only when a message they read has a reaction and the cache has no fresh answer (`lookup_emoji`, as the user groups are asked for). A token whose scopes are known to lack `emoji:read`, from the scopes of its last answer, is not asked, and a `missing_scope` answer is kept as a miss and not written to the log. `TimelineCache::custom_emoji` gives the list of a workspace by name (an empty list when it has none), and `resolve_emoji` says what one name draws as; the emoji picker of S-25 uses the same list, and `slack_emoji_catalog` asks `emoji.list` through `lookup_emoji` when the picker opens and the cache has no fresh answer. `lookup_emoji` asks for one workspace at a time (`emoji_gate`): a call that comes while another asks waits for it and asks again only if the cache still has no fresh answer, so two reads at once send one `emoji.list`.

`resolve_emoji(list, name)` is a pure function. A name the list lacks is not a custom emoji. An entry that is an address is the image when it is `https://` of a host the icons may come from (`icon_host_ok`: `slack-edge.com`, its subdomains such as `emoji.slack-edge.com`, and Gravatar; `icon_url`); any other address, a plain `http://` one, and text that is no address give no image. An entry `alias:other` is followed to `other` (the name is trimmed), at most five times, so a loop or a longer chain gives up and gives no image. An alias that ends on a name the list lacks is a standard emoji when `emojify` knows the name (`alias:white_check_mark` is ✅), and then the reaction is that Unicode emoji and has no image; if `emojify` does not know it, the reaction stays `:name:`. A custom emoji with the name of a standard one is the workspace's own emoji.

`reactions_of` takes the list of the message's workspace, and `Reaction` holds `emoji`, `count`, `name` (Slack's name of the reaction, with a skin tone as it comes, without colons), `image` (the address of the custom emoji's image, otherwise null) and `mine` (S-25). `emoji` is `:name:` for a custom emoji with an image, the Unicode emoji for a standard emoji or for an alias of one, and otherwise what S-22 says. The people who gave a reaction are not kept (S-22).

The screen fetches the image as it fetches the icons of the users: `fetch_images` (Rust gets it from the public host without the token and answers a `data:` URI), through `loadIcons` of `ts/slack-view.ts`, which also takes the addresses of the reactions' images. The fetched images are kept in memory by address, the 500 used last (the avatars and the custom emoji share them); one fetched again when it was dropped. A drawing that finds an icon or an image missing from the kept ones (`decorateAvatar`, `awaitEmoji`) asks for it itself: the URLs of one drawing are gathered and fetched by one `loadIcons` right after it (`requestIcon`; the ones `loadIcons` already has on its way are left out), so a node drawn after the image was dropped is not left as an initial or `:name:`. A reaction or a picker cell waits for its image in a list of the nodes by address (`awaitEmoji`), and only those nodes are painted when it arrives. The CSP is not changed. `reactionsNode` (S-25) draws `:name:` in `.reaction-emoji` first, and puts an `<img class="reaction-img">` there, with the alternative text `:name:`, as soon as the image is here (at once when it was fetched before). An image that cannot be fetched (`fetch_images` leaves it out or fails) leaves `:name:`. The image is as high as the text of the reaction.

`emoji:read` is an optional scope: it is in `OPTIONAL_SCOPES` and in the scope list of the Slack tab of the settings (`OPTIONAL_KINDS` of `ts/permission-pane.ts`, with the other optional scopes and its note in the hint), and a token without it is listed as lacking it with the other optional scopes. It is not in `TIMELINE_SCOPES`, so the list does not warn of it, and a token without it draws `:name:` as before, the rest unchanged.

The unit tests (`cargo test`) cover `resolve_emoji` in `slack.rs` (an image, an alias and an alias of an alias, an alias of a standard emoji, an alias to nothing, the limit of the chain and a loop, and an address that is not `https` or of another host), `reactions_of` with and without a list (`name` and `image`, a custom emoji with the name of a standard one), the rows of a history and a thread message that carry the images, `emoji_of`, the cache (fresh, a miss, `forget`), the scopes (`lacks_emoji_read` and `OPTIONAL_SCOPES` against `TIMELINE_SCOPES`) and `lookup_emoji` against a local port (the call and the kept list, a fresh answer that is not asked for again, a `missing_scope` answer, a token known to lack the scope). The E2E specs `slack-thread.e2e.ts` and `slack-list.e2e.ts` cover the image drawn through `fetch_images` in the thread and in the history (its alternative text, the other reactions unchanged, only the images' addresses fetched), `:name:` kept when the image cannot be fetched or the fetch fails, no fetch when no reaction has an image, and the image drawn when the history is read again; `settings.e2e.ts` covers `emoji:read` in the scope list.

## S-29 Sentry connection of a Slack workspace

The owner gives each connected Slack workspace a Sentry Personal Token, so that the app can work on the Sentry issues that a workspace's Sentry notifications name (the owner's decision of 2026-11-26, issues #1444 and #1447; the buttons that use the token are S-30). This requirement holds the token and the card that keeps it, and nothing else: nothing in the Slack list or the thread changes with it.

**The card.** The Slack tab of the settings has a card "Sentry" (last in the tab, after the card of S-16; the Slack tab's other cards are unchanged). It has the shape of `frontend.md`: a header (the logo `.logo.sentry`, the name, and the `?` hint `#sentry-help`, `aria-label` "Sentry の設定方法"), a row for each workspace that has a token (`#sentry-items`: the avatar of the workspace, its name, the line "…" and the last four characters of the token, the state label "接続済み" (green), and an `.icon-btn` "{workspace} の Sentry のトークンを削除" that asks first, as the unlink of a workspace does), and the add row (`#sentry-form`): a select of the workspaces that have no token (`#sentry-team`), a password field (`#sentry-token`, `aria-label` "Sentry の Personal Token", the placeholder "Personal Token", which only names the field) and "追加". With no workspace the items say "ワークスペースはまだありません", and with workspaces and no token "接続はまだありません"; the add row is off while every workspace has a token or there is no workspace. The `?` hint holds the page that makes a token (`https://sentry.io/settings/account/api/auth-tokens/`), the scopes to choose (`event:write`, `org:read`, `member:read`, `team:read` and `project:read`, with what each is for and a button that copies them) and where the token is kept; the card shows no other help text. The card reads `sentry_connections` each time the settings open, and follows the workspace list: a workspace that is disconnected (the unlink of the Slack card) leaves the card with its row, and a workspace added again starts with none.

**Saving.** `sentry_save(teamId, token)` trims the token and refuses an empty one ("トークンを入力してください") and one that is not printable ASCII with no space ("トークンが正しくありません"), a `teamId` that is not a workspace ID, and a workspace that is not connected ("このワークスペースは接続されていません"). It keeps the token only when Sentry accepts it: `GET https://sentry.io/api/0/organizations/` with `Authorization: Bearer`, a timeout of 15 seconds and no redirect followed. A 2xx answer accepts it; 401 is "トークンが正しくありません", 403 is "トークンの権限が足りません。org:read のスコープを足してください", any other status is "Sentry に確かめられません（{status}）", and a failure to connect is "Sentry に接続できません（…）"; nothing is kept for a refusal. A token kept for the workspace is replaced. The field is emptied as soon as it is read, and an error is shown on a card (A-28). `sentry_delete(teamId)` deletes the token, and `sentry_connections` answers the workspaces that have one with the last four characters of each (`SentryConnection`: `teamId` and `tail`); it asks Sentry nothing, and a listed workspace whose token is gone from the keychain is left out. `sentry_save` and `sentry_delete` answer the connections as `sentry_connections` does. Removing a Slack workspace (`slack_remove_workspace`) deletes its Sentry token too. A failure of that deletion is logged and does not fail the removal.

**Where it is kept.** The token is in the OS keychain (service `jp.mysis.tsunagiai.sentry`, user name the workspace's `team_id`), and the workspaces that have one are in `sentry-connections.json` (`requirements/constraints.md`, "Settings files"). The token is never shown, logged, written to a file, put in an error or returned; the screen gets the last four characters only.

**Not in this requirement.** What the token is used for: Resolve, Archive and the assignee of a Sentry notification in the thread are S-30.

The unit tests (`cargo test`, `sentry.rs`) cover the list of workspaces (once each, taken off alone, saved and read back, a missing file and a file of another shape, team IDs and no token in the file), the check of a token (printable ASCII, no space, no line break that could end the header), the tail of a token (a short one, a multi-byte one), the verdict of a status, and, against a local port, the request (the path, the Bearer credential), 401 and 403 refused, a redirect not followed and not accepted, and a token with a line break refused before anything is sent. The E2E spec `settings.e2e.ts` ("settings: Slack の Sentry") covers the card (its place, the empty note, the select and the password field), the rows read at the start with the tail and the state label, a save (the arguments of `sentry_save` for the workspace chosen, the field emptied, the row drawn from the answer), the add row off when every workspace has a token, a refusal shown on a card with no row, the delete with its confirmation and its cancel and a failed delete keeping the row, the row leaving with its Slack workspace, a failed read written to the log, and the hint's scopes and link.
