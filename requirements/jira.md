# Jira requirements

## J-1 Jira connection

The settings screen has a card 「Jira 接続」 in the tab 「開発」 (the tab `orca`, A-3), the last of its five cards, under the card of the PCs with the server (A-37). The card holds the connection to Jira Cloud: the site's URL, the email address and the API token, a save, and a test of the connection. Rust is `src-tauri/src/jira.rs` (the commands `jira_settings`, `jira_save` and `jira_test`, #868), built like the Todoist connection of T-1 (the token in the keychain, the commands in the service's module); the frontend is `ts/jira-settings.ts`. The site's URL, the authentication, what is saved and where, and what is sent are in `requirements/constraints.md`, "Jira". Only Atlassian Cloud is supported: there is no switch for a self-hosted Jira.

The card is in the shape of the other integrations' cards: the header row (the logo `.logo.orca`, the name 「Jira 接続」 and the `?` hint `#jira-help`, `aria-label` 「Jira 接続の説明」), under it one row (`#jira-items`, the common row of the settings, `itemRow`) with the name 「Jira」, a line and a state label, and the form (`#jira-form`, `.card-add`) with the three fields, 「保存」 (`.text-btn.primary`) and 「接続を試す」 (`#jira-test`, `.text-btn`). The fields are `#jira-site` (`aria-label` and placeholder 「サイトの URL」), `#jira-email` (「メールアドレス」) and `#jira-token` (`type="password"`, 「API トークン」); a placeholder only names its field. The card shows no text about what to type besides the `?` hint (`.claude/rules/frontend.md`).

The row. The line under 「Jira」 is the saved site's URL, and the state label is 「保存済み」 (green) when a site and a token are saved, and 「未設定」 (gray) otherwise. After a test it is 「接続できました」 (green) with the user that Jira answered (the display name and the email address joined by 「 ・ 」, the part Jira did not give is left out) in the line, or 「接続できません」 (orange) after a failed one. A read or a save puts the saved state back.

Reading. `jira_settings` is called each time the tab is shown, and the site and the email address go into the fields; it asks Jira nothing (it reads the file and the keychain) and never returns the token, only `hasToken`. The token field is emptied. Only the latest read draws, and a read that began before a save does not. A failed read writes its message to the log (A-28) and leaves the card as it was.

Saving. 「保存」 (and Enter in a field) calls `jira_save` with `site`, `email` and `token` as typed, and the token field is emptied at once. Rust refuses a site that is not an Atlassian Cloud one, an email address that cannot be a credential and a token with characters a header cannot hold, and a save with no token typed when none is stored; each refusal is a Japanese message shown on a card (A-28), and the form is kept as it was. An empty token keeps the stored one; an empty email address saves a connection that uses a Bearer token. The answer (`site` as Rust normalized it, `email`, `hasToken`) is drawn.

Trying. 「接続を試す」 calls `jira_test` with the same three values, with an empty token meaning the stored one, and saves nothing. Rust sends the credential where Atlassian takes it: with an email address, to the site; with none, through `api.atlassian.com` (the Cloud ID of the site is read first, with no credential), because a scoped token is refused on the site's own URL (`requirements/constraints.md`, "Jira"). The button is disabled until the call ends. A success draws the state and the user; a failure shows its message on a card (A-28), draws 「接続できません」 and enables the button again.

The `?` hint says that only Atlassian Cloud sites (`https://{名前}.atlassian.net`) can be connected, that an email address means Basic authentication with the account's API token and none means Bearer authentication with a scoped token (sent through `api.atlassian.com`), that an empty token in 「保存」 keeps the saved one, that 「接続を試す」 asks Jira who the credential belongs to with the values of the form and saves nothing, and, in its foot, that the token is kept in the keychain and never shown.

Unit tests (`cargo test`, `jira.rs`) cover the site's URL (the accepted forms and their origin, and the refused ones: other hosts, a host that only ends or contains `atlassian.net`, user info, a port, `http`, a dotted or empty name), the email address and the token, the header (Bearer without an email address, Basic with one), the reading of Jira's answer (the user, no email address, an answer that is not JSON, 401 and 403, other statuses with the body cut short), the file (no file, a round trip, a broken file, no token in it), the Cloud ID (the accepted form and what cannot go into a URL), the choice of the base URL (the site for Basic, the gateway with the Cloud ID for Bearer, a site that gives no Cloud ID), and, against local `TcpListener`s that stand for the site and the gateway, the request that is sent for each of the two ways (the path and the Basic or Bearer header, and that the request for the Cloud ID has no credential), a rejected credential, a redirect that is not followed in either call and a host that cannot be reached.
The E2E spec `settings.e2e.ts` ("settings: Jira connection (the 開発 tab, J-1)") covers the tab's name, that the settings are read only when the tab is shown, the card's header, row and form, the states 「未設定」 and 「保存済み」, the arguments of `jira_save` (with an email address and without), a refused save (a card, the form kept), the arguments of `jira_test` (the form's values, an empty token), the button kept off while it waits, the state and the user after a success, a failed test (a card and 「接続できません」), a failed read (the log, no card) and the hint; `settings: tabs` covers the tab's label among the eleven, and the spec of the 開発 tab's cards covers the card's place, last of the five.

Why. The Jira integration (#867) needs a connection that the later parts read the tickets through, so the owner wants to put the site and the credential in once, on a card of their own, and know that they work before anything draws Jira (the owner's decision of 2026-11-19, #868: the card goes in the tab 「開発」, which is the tab 「Orca」 renamed so that it matches the sidebar's button; Atlassian Cloud only; the email address optional, for a scoped token).

## J-2 Jira tickets on the Orca screen

The Orca screen shows the tickets of the Jira that J-1 connects (the parent #867: the list in the right pane, and the ticket in a tab of the work pane). This section holds the parts that are written so far: the commands that read the boards, the sprints and the tickets (#869, `src-tauri/src/jira.rs`), the list in the right pane (#870, `ts/orca-jira.ts`) the ticket in a tab of the work pane (#871, `ts/orca-jira-tab.ts`, with `src-tauri/src/jira/adf.rs`) the edit of its status, assignee, sprint and priority there (#872), and the edit of its description and the adding of a comment (#873, `src-tauri/src/jira/markdown.rs`). The part that comes after (the new ticket) adds its behavior to this section as it comes.

The commands. They read the connection that J-1 saved (`jira-settings.json` and the keychain) and call Jira where `api_base` says (`requirements/constraints.md`, "Jira"), so a Basic credential goes to the site and a Bearer one through the gateway; with no site saved they fail with 「Jira の接続が保存されていません」, and with no token with 「API トークンを入力してください」. The commands below only read: they change nothing in Jira, in the settings or in the keychain, and the token is never returned. The ones that write are in "Editing the fields" below. A failure is a Japanese message (A-28), the same as J-1's: 「Jira が認証を拒否しました（401）」 for 401 and 403, and 「Jira が {status} を返しました: {the first 200 characters of the body}」 for the others. They read at a call and nothing at an interval.

- `jira_boards` gives the boards that the credential can see, by name, as `{id, name, type}` (`type` is Jira's `scrum`, `kanban` or `simple`; only a scrum board has sprints). At most 200.
- `jira_sprints(boardId)` gives the active and future sprints of a board, the active one first, as `{id, name, state, startDate, endDate}` (`state` is `active` or `future`; the dates are Jira's ISO 8601 text, `null` for a sprint that has not started). At most 100. A board that has no sprints (a kanban one) is Jira's refusal, shown as its message; the screen asks for the sprints of a scrum board only.
- `jira_sprint_issues(sprintId)` gives the tickets of a sprint in the order of the board's rank, and `jira_backlog(boardId)` the backlog of a board (its incomplete tickets that no active or future sprint holds), in the same order. Both answer `{issues, truncated}`: each ticket is `{key, summary, status, statusCategory, assignee, priority}`, where `statusCategory` is the key of the status's category (`new`, `indeterminate` or `done`, `undefined` when Jira gave none), `assignee` is the display name and `null` when unassigned, and `priority` is the name and `null` when the project has no priority. At most 500 tickets, and `truncated` is `true` when there were more.
- `jira_issue(key)` gives one ticket for its tab (#871), as `{key, summary, description, status, statusCategory, assignee, priority, sprint, labels, parent, comments, commentsTruncated}`. `description` and the `body` of each comment are Markdown, read from Jira's ADF ("ADF as Markdown" below), `""` when there is none. `sprint` is the name of the sprint the ticket is in now, `null` for none; `labels` is a list of names; `parent` is `{key, summary}` or `null`; `status`, `statusCategory`, `assignee` and `priority` are as the list has them. A comment is `{author, created, body}` with `created` as `YYYY-MM-DD HH:MM` in the offset Jira gave (the one of the credential's user), and the comments are oldest first, at most 200, with `commentsTruncated` `true` when there were more. `key` is checked before anything is asked: a capital letter, then capitals, digits and underscores, a hyphen and a number, at most 64 characters, so that only a ticket key reaches the path; another form fails with 「チケットのキーの形が正しくありません」.

What Jira is asked: the Agile API of Jira Software Cloud, `GET /rest/agile/1.0/board?orderBy=name`, `/board/{boardId}/sprint?state=active,future`, `/sprint/{sprintId}/issue?fields=summary,status,assignee,priority` and `/board/{boardId}/backlog?fields=…`, each with `startAt` and `maxResults=50`, page after page until `isLast`, the `total` or an empty page, or until the limit above (the next page starts after what a page gave, so a page shorter than asked does not end the list). The ids are numbers, so nothing typed reaches the path. A ticket is read with three calls one after another, and a refusal of any is the failure of the whole read: `GET /rest/api/3/issue/{key}?fields=summary,description,status,assignee,priority,labels,parent` (REST API v3, whose description is ADF), `GET /rest/agile/1.0/issue/{key}?fields=sprint` (the sprint is a custom field in v3, whose id differs by site; the Agile API gives it as `fields.sprint`) and `GET /rest/api/3/issue/{key}/comment?orderBy=created` with the same pages (the answer has `comments`, `total`, `startAt` and `maxResults`). The shapes were read from Atlassian's Jira Software Cloud REST API description (`swagger.v3.json` of `dac-static.atlassian.com/cloud/jira/software`, read on 2026-11-25): the pages of boards and sprints have `values`, `isLast`, `startAt` and `total`, the pages of tickets have `issues`, `startAt` and `total`, and a ticket's `fields` has `summary`, `status` (with its `statusCategory`), `assignee` and `priority`. For the ticket's tab the same documents (and `swagger-v3.v3.json` of `dac-static.atlassian.com/cloud/jira/platform`, read on 2026-11-25) give `fields.description` (ADF), `labels`, `parent` (`key` and `fields.summary`), the comments with `author.displayName`, `body` (ADF) and `created`, and, of the Agile API's issue, `fields.sprint` with its `name`. The scopes of the Agile issue read are `read:issue:jira-software` and, of the comment read, `read:comment:jira` (and the others of the beta list there); a scoped token needs them.

ADF as Markdown. `adf_to_markdown` (`src-tauri/src/jira/adf.rs`) is a pure function from the ADF document to Markdown, and it never fails. The node types are those of Atlassian's ADF schema (the JSON schema of `@atlaskit/adf-schema`, `unpkg.com/@atlaskit/adf-schema/dist/json-schema/v1/full.json`, read on 2026-11-25). It reads: paragraphs, headings (level 1 to 6), bullet and ordered lists (with their start number) nested by the width of the marker, task items as `☐` and `☑`, decision items as bullets, code blocks (the language when it is a plain word, a fence longer than any run of backticks in the code), block quotes and panels as quotes, rules, tables (the first row is the header, short rows are filled up, the lines of a cell joined with `<br>`; merged cells are not kept), expands (the title in bold, then the content), layout columns (their blocks), and, in a line, the marks strong, em, strike and code and links, hard breaks, mentions (`@name`), emoji, dates (`YYYY-MM-DD`, in UTC), statuses (`[text]`), cards (a link to the address) and placeholders. Colors, underline, sub and superscript, alignment and sizes are not kept. A file of Jira (`media`) is a note, 「（添付ファイル）」 with its alt text, because it cannot be read without the credential, and a picture of the web is a link and never an image, so that the page loads nothing from outside. A link keeps `http` and `https` addresses only, and what would end its address is written as a percent code. The text is Jira's, not the app's, so what Markdown would read as markup (`* _ [ ] < > & ~ | ` and a backtick, and at the start of a line `#`, `+`, `-`, `=`, `>` and a number with `.` or `)`) is written with a backslash. A node it does not know shows the text it holds, or nothing; nodes deeper than 40 levels are dropped.

Unit tests (`cargo test`, `jira.rs` and `jira/adf.rs`) cover the end of a list (`isLast`, `total`, an empty page, and going on by what was received), the reading of a page of boards, sprints and tickets (the fields Jira leaves out or sets to null, and the ones the app does not use), the failures (401 and 403, other statuses, an answer that is not JSON), the saved connection that the commands read (no site, no token), and, against local `TcpListener`s that stand for the site and the gateway, the paths and queries that are sent for each of the four reads (with the Basic or the Bearer header, and with the Cloud ID read with no credential), the second page of a list, the stop at the limit with `truncated`, a refused read and a redirect that is not followed. For `jira_issue` they cover the key (the accepted forms, and what must not reach a path: an empty one, lowercase, a path, a query, a fragment, an encoded slash, a full-width digit, and a key over the limit), the time of a comment (the offset kept, other texts kept as they are), the sprint (none, an empty name, a refusal, an answer that is not JSON), the ticket with the fields Jira leaves out, the description and the comments gathered into the answer, the three paths and the credential that are sent, a bad key that asks nothing, and a refusal of any of the three reads. The conversion of ADF is covered node by node: the marks and the spaces around them, code spans, links (only web addresses, the characters that end an address), the escaping of text and of what starts a line, hard breaks, headings, nested and ordered lists, task and decision items, code blocks, quotes and panels, rules, tables, mentions, emoji, dates, statuses and cards, files and pictures, expands, nodes it does not know, nodes that are too deep, a document that is not an object, and one description of several parts. E2E has nothing to check for the commands themselves: the screen's part is below. The writes of #872 (`jira_transitions`, `jira_transition`, `jira_assignable`, `jira_assign`, `jira_priorities`, `jira_set_priority` and `jira_set_sprint`) have their unit tests in `jira.rs` too: the ids (numbers only for a transition and a priority, an account id that cannot be `-1`), the reading of the answers (the transitions that can be taken, the active people, the allowed priorities, a 2xx as done and the reason otherwise) and, against local `TcpListener`s, the method, the path, the Basic or Bearer header and the body of each write, a bad id that asks nothing, a refusal with its reason and a redirect that is not followed.

The list in the right pane. The top row of the file pane (A-18) has a fifth button, 「Jira」 (`#orca-files-mode-jira`, `aria-label` 「Jira」, after 「データベース」), that shows the tickets under the row as 「履歴」 shows the history (A-27). The choice is kept in memory only. The tickets belong to no worktree, so the part (`#orca-jira`) hides the heading of the pane (`#orca-files-head`), as the database part does (A-43). The reads of the files (the return of the focus, the clock of the screen) do not read the tickets by the clock; see "Reading" below.

Reading. Each time the part comes to be shown it calls `jira_settings`, which asks Jira nothing. With no site or no token saved, the part says 「Jira に接続されていません」 and has 「設定を開く」, which opens the tab 「開発」 of the settings (J-1, `#settings-tab-orca`); nothing else is called. The connection is read again when the screen is shown after that press, and when the window gets the focus back while it is still missing or the first read failed. With a connection, `jira_boards` is called and only the boards of type `scrum` are kept (a kanban board has no sprints); with none the part says 「スクラムボードがありません」. The first scrum board is chosen, and a select `#orca-jira-board` (`aria-label` 「ボード」) is shown only when there is more than one; choosing another reads its sprints and its backlog. `jira_sprints(boardId)` gives the sprints (the active one first), and the select `#orca-jira-sprint` (「スプリント」) holds 「すべてのスプリント」 and each sprint by name; the first sprint is chosen at first, so the tickets of one sprint are read, not of all. The list is made of sections, one for each sprint that the choice names (in the order Jira gave) and, last and always, the backlog (`jira_backlog(boardId)`). The tickets of a section are read (`jira_sprint_issues(sprintId)`) one section after another, and a section that was read is not read again by a new choice of the sprint. 「再読み込み」 (`#orca-jira-reload`, an icon button) reads everything again. Nothing is read at an interval.

The sections. Each has a head (`.orca-jira-head`) with the name of the sprint (or 「バックログ」), 「進行中」 for the active sprint or 「予定」 for a future one, and, once read, the number of the rows drawn (「3 件」). A section that is being read shows a waiting row, and one whose read failed shows its message and 「再読み込み」, which reads that section alone; the other sections stay. When Jira has more tickets than the command reads (`truncated`), the section ends with 「{n} 件で打ち切りました」. A failed read is written to the log (A-28, source `orca-jira`) and drawn in the part; no card is shown for it.

The rows. A ticket is a row (`.orca-jira-issue`, `data-key`, `data-category` is the status category) of its key, its summary and its status as a label (gray for `new`, blue for `indeterminate`, green for `done`). A ticket whose category is `done` has its key and summary struck through and muted. A double press on a row opens the ticket in a tab of the work pane (below); one press does nothing. The select `#orca-jira-status` (「ステータス」) holds 「すべてのステータス」 and the status names of the tickets read so far, in the order they were met, and narrows every section to the status chosen, with the counts following; the choices of the sprint and of the status are kept while the part is read again. The part shows no help text and its fields have no placeholder (`.claude/rules/frontend.md`).

The ticket's tab (#871). A double press on a row (the page's `dblclick`, as a file of A-18) opens the ticket as a tab of the work pane (A-8, A-17), like the tab of a diff (A-24): it joins the strip of the pane with the focus, after the tabs it has, with the ticket mark (`TICKET_SVG`) in place of the status icon, its title is the ticket's key, it is selected, and it is closed with its close button (which asks nothing: a description or a comment that was typed and not saved goes with the tab). Its id is `jira:{n}`, `data-jira` is "true" on it, and A-17 keeps it in the layout as it keeps `diff:{n}`: the layout holds the id only, and the tab is in memory only (by target and project, as the tabs of the files are), so after a restart the id is dropped from the layout. It is not a session, so it has no row in the list of A-8. A ticket that is open in the project already is selected and read again, and no second tab is opened; another ticket has a tab of its own. It has the main worktree of its project as its worktree, so the file pane shows the files of that worktree while the tab is selected, and the Jira part of the file pane stays as it was (A-43 does the same for a database tab). Its menu has the split rows of A-17 only: it has no window of its own (A-46).
- The page (`.orca-jira-tab`, in the host of the editor of its pane). The heading (`.orca-edit-head`) has the key and an icon button 「読み直す」, which is off while the ticket is read. The body has two columns. The main one (`.orca-jira-main`) has the key line (the parent's key, a slash and the ticket's key, or the key alone; the parent's summary is the title of the parent's key), the summary (`h2`), the description as Markdown (nothing when there is none), and the comments: a head 「コメント {n} 件」, and for each comment its author, its time and its text as Markdown, oldest first, and 「{n} 件で打ち切りました」 when Rust says there were more. The right column (`.orca-jira-side`) has six rows, each a name and a value: 「ステータス」 (a label colored by its category, as the list's), 「担当」 (「未割り当て」 when none), 「スプリント」, 「優先度」, 「ラベル」 (each label as a chip) and 「親」 (the parent's key and summary), and 「なし」 in gray for what the ticket does not have. The status, the assignee, the sprint and the priority are changed here ("Editing the fields" below); the labels and the parent are shown only.
- Reading. `jira_issue({key})` is called when the tab is opened and when it is opened again, and by 「読み直す」, never by the clock. While it is read the first time the body is a waiting row; the ticket that was shown stays while a new read goes on. A read that ends after the tab was closed, or after a newer read began, is dropped. A failure drops the ticket and shows its message in place of the body (`.orca-file-note.fail`), writes it to the log (A-28, source `orca-jira`) and shows no card; 「読み直す」 reads it again.
- The text. The description and the comments come as Markdown and are drawn through `markdownHtml` of `ts/todo-data.ts`, the one that draws the descriptions and the comments of Todoist: only http(s) links stay, and forms, fields, buttons, styles, ids, classes and `data-*` are dropped, because the text is another person's. A link navigates the page, which Rust hands to the default browser (as a Todo's does). The tab shows no help text and its fields have no placeholder (`.claude/rules/frontend.md`).

Editing the fields (#872). In the right column the values of 「ステータス」, 「担当」, 「スプリント」 and 「優先度」 are buttons (`.orca-jira-edit`, the same text as before: the status as its label, 「未割り当て」 and 「なし」 in gray), and the labels and the parent are not. Pressing one asks Jira for what that field can take now and opens a menu under it (`ts/menu.ts`); the options are not read with the ticket. While they are read the button is off, and a failed read is a card (A-28, source `orca-jira`) with no menu. A menu with nothing to choose says 「選べるものがありません」. Choosing the value that the ticket has does nothing.
- 「ステータス」: `jira_transitions({key})` gives the changes of status that the ticket can take now (`isAvailable` is not false), each with the status it leads to, and the menu lists those statuses except the ticket's own, so only the transitions of this ticket are offered. A choice calls `jira_transition({key, transitionId})`. A transition that needs fields of its own (a screen) is refused by Jira with its reason, which is shown.
- 「担当」: `jira_assignable({key})` gives the people the ticket can be assigned to (at most 100: Jira's search of assignable users with no text), and the menu is 「未割り当て」 and each person, with a field (`aria-label` 「担当を探す」) that narrows them. A choice calls `jira_assign({key, accountId})`, with `accountId` `null` for 「未割り当て」.
- 「優先度」: `jira_priorities({key})` gives the priorities that the edit metadata of the ticket allows (none when this credential cannot edit its priority), and a choice calls `jira_set_priority({key, priorityId})`.
- 「スプリント」: the menu is 「バックログ」 and the active and future sprints of the board that the list was showing when the tab was opened (`jira_sprints({boardId})`, the call of the list), and a choice calls `jira_set_sprint({key, sprintId})`, with `sprintId` `null` for 「バックログ」. A ticket that is open again from the list takes the board of that list.
- The new value is shown at once, and the four buttons and 「読み直す」 are off until Jira answers (one change at a time, and the ticket is not read meanwhile). When Jira refuses, the old value comes back, a card shows Jira's reason (A-28) and the log has it. When Jira takes it, the tab keeps the value (the ticket is not read again) and the list in the right pane follows: the rows of the ticket take the new status and its category; for a change of the sprint the sections that were read are read again, because where the ticket stands is Jira's. A list that is not shown reads everything when it is shown, as it always does.
- What Rust sends is in `requirements/constraints.md`, "Jira": the key, the ids of a transition and a priority and the account id are checked before they reach a path or a body.

Editing the description and adding a comment (#873). The description and the comments are edited in the rich Markdown editor of A-26: the Milkdown bundle that the Slack posting fields and the mail reply use (`createRichEditor` of `ts/rich-editor.ts`, which loads it the first time), with its toolbar and with no send arrow of its own.
- The description. A pencil (`.orca-jira-desc-edit`, `aria-label` 「説明を編集」) at the right of the description, also when there is none, opens the editor (`#orca-jira-desc-input`) in place of the text, filled with the Markdown the tab was given, and under it 「保存」 (`.orca-jira-save`, `.text-btn.primary`, also Cmd+Enter, or Ctrl+Enter off macOS) and 「キャンセル」 (`.orca-jira-cancel`). While it is open the button 「読み直す」 is off. 「キャンセル」 shows the text again and calls nothing. 「保存」 calls `jira_set_description({key, base, markdown})`, where `base` is the Markdown the editor was opened with (not the editor's text) and `markdown` is what the editor exports; the editor, the two buttons, the four fields and 「読み直す」 are off until Jira answers. The answer is the Markdown of what Jira now holds: it is drawn as the description, the editor is gone, and the ticket is not read again. When Jira refuses, the ticket keeps the description it had, a card shows the reason (A-28, source `orca-jira`), and the editor stays open with the typing in it. The editor has no placeholder and the tab no help text (`.claude/rules/frontend.md`).
- A comment. 「コメントを追加」 (`.orca-jira-comment-add`) under the comments opens a second editor (`#orca-jira-comment-input`) with 「追加」 (`.orca-jira-comment-submit`, off while the field holds no text; also Cmd+Enter) and 「キャンセル」 (`.orca-jira-comment-cancel`, which empties the field and closes it). 「追加」 calls `jira_add_comment({key, markdown})`; the comment that Jira answers with (`{author, created, body}`, as `jira_issue` gives one) is put under the others, the head counts it, the field is emptied and closed, and the ticket is not read again. When Jira refuses, a card shows the reason, the text stays in the field, and no comment is added. A comment is only added: none is edited or deleted.
- Markdown back to ADF. Rust turns the Markdown into Jira's document (`jira/markdown.rs`, pure functions, and only `pulldown-cmark`, which the app has): paragraphs, headings (a heading inside a list item or a quote is a bold paragraph, because ADF has none there), bullet and ordered lists (with their start number), task lists (items marked `- [ ]`, `- [x]`, `☐` or `☑`, when every item of the list is one and has one line; any other list keeps the mark as its character), code blocks (a language that is a plain word), quotes (a quote in a list item is its content, and a rule there is dropped), rules, tables (the first row is the header), the marks strong, em, strike and code (code takes no other style; ADF allows a link only), links, and hard breaks (also `<br>`, as the reading writes a table cell's lines). A link keeps `http` and `https` addresses only; a picture is its alt text as a link (never an image), and other HTML is text. A task list and a task item get a `localId`, which ADF requires, that no other node of the document holds.
- What Markdown cannot say is not lost. The description is not made again from the Markdown: `jira_set_description` reads the description Jira holds now (`GET /rest/api/3/issue/{key}?fields=description`), refuses with 「説明が Jira で変更されています。読み直してください」 when it is not the `base` (read as Markdown the same way), and puts the new Markdown into that document (`merged`). Every block of the old document is written as Markdown and read again by the same parser as the new text, and the two lists of blocks are matched by their longest common run, so the notation of the editor (`*` or `_`, a bullet mark, a link in angle brackets) does not make a block changed. A block of the new text that equals an old one is the old block as Jira has it, with its mentions, statuses, files, panels, expands, merged cells, colors, underline and every other node Markdown does not hold. A list and a quote are matched in the same way item by item and block by block, so editing one item leaves the others as they are. A block that was changed is made from the Markdown, with the mentions, emoji, dates, statuses and cards of the old line put back where their text (`@name`, `:name:`, `YYYY-MM-DD`, `[text]`, the address of a card) still stands after the one before it. A block that is nothing as Markdown (a macro, an empty paragraph) is not in the editor and is always kept where it stands. Bullet, task and decision lists that stand one after another, and ordered ones, are one list in Markdown (and in the editor) and so are read as one. What a changed block loses: the underline, color, size and alignment of its text, a panel's kind (a changed panel becomes a quote), the merged cells, widths and colors of a changed table, the files and expands inside it, and a decision list (a changed one becomes a bullet list). What the owner takes out of the text is taken out of the document. A save that changes nothing sends nothing, and an empty text saves a description of `null`.
