# Jira requirements

## J-1 Jira connection

The settings screen has a card 「Jira 接続」 in the tab 「開発」 (the tab `orca`, A-3), the last of its five cards, under the card of the PCs with the server (A-37). The card holds the connection to Jira Cloud: the site's URL, the email address and the API token, a save, and a test of the connection. Rust is `src-tauri/src/jira.rs` (the commands `jira_settings`, `jira_save` and `jira_test`, #868), built like the Todoist connection of T-1 (the token in the keychain, the commands in the service's module); the frontend is `ts/jira-settings.ts`. The site's URL, the authentication, what is saved and where, and what is sent are in `requirements/constraints.md`, "Jira". Only Atlassian Cloud is supported: there is no switch for a self-hosted Jira.

The card is in the shape of the other integrations' cards: the header row (the logo `.logo.orca`, the name 「Jira 接続」 and the `?` hint `#jira-help`, `aria-label` 「Jira 接続の説明」), under it one row (`#jira-items`, the common row of the settings, `itemRow`) with the name 「Jira」, a line and a state label, and the form (`#jira-form`, `.card-add`) with the three fields, 「保存」 (`.text-btn.primary`) and 「接続を試す」 (`#jira-test`, `.text-btn`). The fields are `#jira-site` (`aria-label` and placeholder 「サイトの URL」), `#jira-email` (「メールアドレス」) and `#jira-token` (`type="password"`, 「API トークン」); a placeholder only names its field. The card shows no text about what to type besides the `?` hint (`.claude/rules/frontend.md`).

The row. The line under 「Jira」 is the saved site's URL, and the state label is 「保存済み」 (green) when a site and a token are saved, and 「未設定」 (gray) otherwise. After a test it is 「接続できました」 (green) with the user that Jira answered (the display name and the email address joined by 「 ・ 」, the part Jira did not give is left out) in the line, or 「接続できません」 (orange) after a failed one. A read or a save puts the saved state back.

Reading. `jira_settings` is called each time the tab is shown, and the site and the email address go into the fields; it asks Jira nothing (it reads the file and the keychain) and never returns the token, only `hasToken`. The token field is emptied. Only the latest read draws, and a read that began before a save does not. A failed read writes its message to the log (A-28) and leaves the card as it was.

Saving. 「保存」 (and Enter in a field) calls `jira_save` with `site`, `email` and `token` as typed, and the token field is emptied at once. Rust refuses a site that is not an Atlassian Cloud one, an email address that cannot be a credential and a token with characters a header cannot hold, and a save with no token typed when none is stored; each refusal is a Japanese message shown on a card (A-28), and the form is kept as it was. An empty token keeps the stored one; an empty email address saves a connection that uses a Bearer token. The answer (`site` as Rust normalized it, `email`, `hasToken`) is drawn.

Trying. 「接続を試す」 calls `jira_test` with the same three values, with an empty token meaning the stored one, and saves nothing. Rust sends the credential where Atlassian takes it: with an email address, to the site; with none, through `api.atlassian.com` (the Cloud ID of the site is read first, with no credential), because a scoped token is refused on the site's own URL (`requirements/constraints.md`, "Jira"). The button is disabled until the call ends. A success draws the state and the user; a failure shows its message on a card (A-28), draws 「接続できません」 and enables the button again.

The `?` hint says that only Atlassian Cloud sites (`https://{名前}.atlassian.net`) can be connected, that an email address means Basic authentication with the account's API token and none means Bearer authentication with a scoped token (sent through `api.atlassian.com`), that an empty token in 「保存」 keeps the saved one, that 「接続を試す」 asks Jira who the credential belongs to with the values of the form and saves nothing, and, in its foot, that the token is kept in the keychain and never shown.

Unit tests (`cargo test`, `jira.rs`) cover the site's URL (the accepted forms and their origin, and the refused ones: other hosts, a host that only ends or contains `atlassian.net`, user info, a port, `http`, a dotted or empty name), the email address and the token, the header (Bearer without an email address, Basic with one), the reading of Jira's answer (the user, no email address, an answer that is not JSON, 401 and 403, other statuses with the body cut short), the file (no file, a round trip, a broken file, no token in it), the Cloud ID (the accepted form and what cannot go into a URL), the choice of the base URL (the site for Basic, the gateway with the Cloud ID for Bearer, a site that gives no Cloud ID), and, against local `TcpListener`s that stand for the site and the gateway, the request that is sent for each of the two ways (the path and the Basic or Bearer header, and that the request for the Cloud ID has no credential), a rejected credential, a redirect that is not followed in either call and a host that cannot be reached.
The E2E spec `settings.e2e.ts` ("settings: Jira connection (the 開発 tab, J-1)") covers the tab's name, that the settings are read only when the tab is shown, the card's header, row and form, the states 「未設定」 and 「保存済み」, the arguments of `jira_save` (with an email address and without), a refused save (a card, the form kept), the arguments of `jira_test` (the form's values, an empty token), the button kept off while it waits, the state and the user after a success, a failed test (a card and 「接続できません」), a failed read (the log, no card) and the hint; `settings: tabs` covers the tab's label among the eleven, and the spec of the 開発 tab's cards covers the card's place, last of the five.

Why. The Jira integration (#867) needs a connection that the later parts read the tickets through, so the owner wants to put the site and the credential in once, on a card of their own, and know that they work before anything draws Jira (the owner's decision of 2026-11-19, #868: the card goes in the tab 「開発」, which is the tab 「Orca」 renamed so that it matches the sidebar's button; Atlassian Cloud only; the email address optional, for a scoped token).

## J-2 Jira tickets on the Orca screen

The Orca screen shows the tickets of the Jira that J-1 connects (the parent #867: the list in the right pane, and the ticket in a tab of the work pane). This section holds the parts that are written so far: the commands that read the boards, the sprints and the tickets (#869, `src-tauri/src/jira.rs`) and the list in the right pane (#870, `ts/orca-jira.ts`). The parts that come after (the ticket's tab, the edits and the new ticket) add their behavior to this section as they come.

The commands. They read the connection that J-1 saved (`jira-settings.json` and the keychain) and call Jira where `api_base` says (`requirements/constraints.md`, "Jira"), so a Basic credential goes to the site and a Bearer one through the gateway; with no site saved they fail with 「Jira の接続が保存されていません」, and with no token with 「API トークンを入力してください」. They only read: they change nothing in Jira, in the settings or in the keychain, and the token is never returned. A failure is a Japanese message (A-28), the same as J-1's: 「Jira が認証を拒否しました（401）」 for 401 and 403, and 「Jira が {status} を返しました: {the first 200 characters of the body}」 for the others. They read at a call and nothing at an interval.

- `jira_boards` gives the boards that the credential can see, by name, as `{id, name, type}` (`type` is Jira's `scrum`, `kanban` or `simple`; only a scrum board has sprints). At most 200.
- `jira_sprints(boardId)` gives the active and future sprints of a board, the active one first, as `{id, name, state, startDate, endDate}` (`state` is `active` or `future`; the dates are Jira's ISO 8601 text, `null` for a sprint that has not started). At most 100. A board that has no sprints (a kanban one) is Jira's refusal, shown as its message; the screen asks for the sprints of a scrum board only.
- `jira_sprint_issues(sprintId)` gives the tickets of a sprint in the order of the board's rank, and `jira_backlog(boardId)` the backlog of a board (its incomplete tickets that no active or future sprint holds), in the same order. Both answer `{issues, truncated}`: each ticket is `{key, summary, status, statusCategory, assignee, priority}`, where `statusCategory` is the key of the status's category (`new`, `indeterminate` or `done`, `undefined` when Jira gave none), `assignee` is the display name and `null` when unassigned, and `priority` is the name and `null` when the project has no priority. At most 500 tickets, and `truncated` is `true` when there were more.

What Jira is asked: the Agile API of Jira Software Cloud, `GET /rest/agile/1.0/board?orderBy=name`, `/board/{boardId}/sprint?state=active,future`, `/sprint/{sprintId}/issue?fields=summary,status,assignee,priority` and `/board/{boardId}/backlog?fields=…`, each with `startAt` and `maxResults=50`, page after page until `isLast`, the `total` or an empty page, or until the limit above (the next page starts after what a page gave, so a page shorter than asked does not end the list). The ids are numbers, so nothing typed reaches the path. The shapes were read from Atlassian's Jira Software Cloud REST API description (`swagger.v3.json` of `dac-static.atlassian.com/cloud/jira/software`, read on 2026-11-25): the pages of boards and sprints have `values`, `isLast`, `startAt` and `total`, the pages of tickets have `issues`, `startAt` and `total`, and a ticket's `fields` has `summary`, `status` (with its `statusCategory`), `assignee` and `priority`.

Unit tests (`cargo test`, `jira.rs`) cover the end of a list (`isLast`, `total`, an empty page, and going on by what was received), the reading of a page of boards, sprints and tickets (the fields Jira leaves out or sets to null, and the ones the app does not use), the failures (401 and 403, other statuses, an answer that is not JSON), the saved connection that the commands read (no site, no token), and, against local `TcpListener`s that stand for the site and the gateway, the paths and queries that are sent for each of the four reads (with the Basic or the Bearer header, and with the Cloud ID read with no credential), the second page of a list, the stop at the limit with `truncated`, a refused read and a redirect that is not followed. E2E has nothing to check for the commands themselves: the screen's part is below.

The list in the right pane. The top row of the file pane (A-18) has a fifth button, 「Jira」 (`#orca-files-mode-jira`, `aria-label` 「Jira」, after 「データベース」), that shows the tickets under the row as 「履歴」 shows the history (A-27). The choice is kept in memory only. The tickets belong to no worktree, so the part (`#orca-jira`) hides the heading of the pane (`#orca-files-head`), as the database part does (A-43). The reads of the files (the return of the focus, the clock of the screen) do not read the tickets by the clock; see "Reading" below.

Reading. Each time the part comes to be shown it calls `jira_settings`, which asks Jira nothing. With no site or no token saved, the part says 「Jira に接続されていません」 and has 「設定を開く」, which opens the tab 「開発」 of the settings (J-1, `#settings-tab-orca`); nothing else is called. The connection is read again when the screen is shown after that press, and when the window gets the focus back while it is still missing or the first read failed. With a connection, `jira_boards` is called and only the boards of type `scrum` are kept (a kanban board has no sprints); with none the part says 「スクラムボードがありません」. The first scrum board is chosen, and a select `#orca-jira-board` (`aria-label` 「ボード」) is shown only when there is more than one; choosing another reads its sprints and its backlog. `jira_sprints(boardId)` gives the sprints (the active one first), and the select `#orca-jira-sprint` (「スプリント」) holds 「すべてのスプリント」 and each sprint by name; the first sprint is chosen at first, so the tickets of one sprint are read, not of all. The list is made of sections, one for each sprint that the choice names (in the order Jira gave) and, last and always, the backlog (`jira_backlog(boardId)`). The tickets of a section are read (`jira_sprint_issues(sprintId)`) one section after another, and a section that was read is not read again by a new choice of the sprint. 「再読み込み」 (`#orca-jira-reload`, an icon button) reads everything again. Nothing is read at an interval.

The sections. Each has a head (`.orca-jira-head`) with the name of the sprint (or 「バックログ」), 「進行中」 for the active sprint or 「予定」 for a future one, and, once read, the number of the rows drawn (「3 件」). A section that is being read shows a waiting row, and one whose read failed shows its message and 「再読み込み」, which reads that section alone; the other sections stay. When Jira has more tickets than the command reads (`truncated`), the section ends with 「{n} 件で打ち切りました」. A failed read is written to the log (A-28, source `orca-jira`) and drawn in the part; no card is shown for it.

The rows. A ticket is a row (`.orca-jira-issue`, `data-key`, `data-category` is the status category) of its key, its summary and its status as a label (gray for `new`, blue for `indeterminate`, green for `done`). A ticket whose category is `done` has its key and summary struck through and muted. The rows take no press yet (the ticket's tab is a later part). The select `#orca-jira-status` (「ステータス」) holds 「すべてのステータス」 and the status names of the tickets read so far, in the order they were met, and narrows every section to the status chosen, with the counts following; the choices of the sprint and of the status are kept while the part is read again. The part shows no help text and its fields have no placeholder (`.claude/rules/frontend.md`).

E2E (`orca-jira.e2e.ts`) covers the button and its place in the top row (the list of the buttons is also in `orca-files.e2e.ts`), that nothing is read before the part is shown and that the heading is hidden, the missing connection and the way to the settings and back, the commands and their arguments for a connection (the boards, the sprints, the first sprint, the backlog), the rows and their texts, the strike-through of a ticket that is done and the different colors of the three categories, the select of the sprints (the options, `すべて`, one sprint, a section read once), the status filter and the counts, the choice among several scrum boards, a connection with no scrum board, a section that failed beside one that did not (the message, the log, no card, the retry), a failed read of the boards and its retry, `truncated`, the reload button, and that the part reads again each time it is shown and not at an interval. The commands' own behavior is in the unit tests above.

Why. The list and the ticket tab of the Jira integration (#867, the owner's decision of 2026-11-17: the right pane lists, the work pane's tab shows the ticket) need the data first, and the shapes of Jira's answers are the part that can be wrong, so they are read and checked on their own before any screen draws them (#869).
