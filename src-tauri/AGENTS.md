# つなぎAI: the Rust backend

This file is the part of the developer guide (`AGENTS.md` of the root) for `src-tauri/`: the modules and what `tsunagiai-mcp` offers.
Claude Code and other agents read it when they work under `src-tauri/`.

## Modules

The modules are in the library crate (`src/lib.rs`), and `main.rs` only calls `tsunagiai_lib::run()`.
Each service has its own module:

- `gmail.rs`, with `gmail/held.rs` (the opened threads held in memory for a reopen, M-2)
- `calendar.rs` (Google Calendar, and the check of the candidates of free time of `calendar_show_slots`, C-6), `todoist.rs` (Todoist)
- `jira.rs` (J-1, #868): the connection to Jira Cloud: the site's URL and the email address in `jira-settings.json`, the API token in the keychain, and the test of the connection (`jira_settings`, `jira_save` and `jira_test`)
- `notion.rs`: Notion's MCP server (the OAuth connection and the tokens, and the lists of favorites, teamspaces and teamspace pages, with `notion/pages.rs` reading the replies)
- `slack.rs`, with `slack_markdown.rs` (Markdown to Slack's mrkdwn, S-6 and S-21), `slack_mrkdwn.rs` (Slack's mrkdwn read as the structure the thread draws, S-12), `slack_blocks.rs` (a message's blocks and attachments, S-11), `slack_emoji.rs` (the Slack emoji names that the `emojis` crate lacks), `slack/emoji_usage.rs` (the emoji the owner reacted with, kept per workspace in `slack-emoji-usage.json`, and the order the picker shows them in, S-25) and `slack/socket.rs` (the Socket Mode connection, S-16)
- `claude.rs`, with `claude_auth.rs` (how `claude -p` is signed in, A-4) and `claude_code.rs` (the shared part of the Claude Code panes, A-36: the pseudo terminal opened with `portable-pty`, and the folder `claude-code/` with its launch script and `mcp.json` for `tsunagiai-mcp` (the calendar pane starts in the `auto` permission mode, with `start-auto.sh` and `mcp-calendar.json`, #1074, and the pane of a Todo's draft in `auto-todo-draft`, with `start-auto-todo-draft.sh` and `mcp-todo-draft.json`, Sonnet at the effort high, #1148), and the first instruction a screen gives a pane, passed as the value of `--append-system-prompt`, #976, #1293; the orchestrator's still follows a `--`)
- `screen_bridge.rs` (A-36, #731): the Unix socket `screen-bridge.sock` of the config directory through which `tsunagiai-mcp` reads and writes the fields a screen holds (`screen_read`, `screen_write`), and tells the app that something changed, with `ts/screen-bridge.ts` where a screen registers its target
- `skills.rs`: the skills of the Claude calls, saved as `SKILL.md` files in `claude-plugin/` of the config directory
- `formation.rs` (A-37): the orchestration: the folder `formations/{name}/` of each formation with its `formation.json` and `children.json`, and the tools `formation_plan`, `formation_launch` and `formation_close` of `tsunagiai-mcp` behind `--formation`, which start and end the children in Orca, and `formation_stop` (#1132), which closes only a child's terminal. Each Claude Code child is a Dispatch of the formation's Run of Orca's orchestration (#1237; a Codex child has none): `formation_launch` makes the Run once (`runId` of `formation.json`) and a task and a Dispatch for the child (`dispatches`), with the preamble in front of its first instruction, and answers `runId` and `dispatchId` (both null for a Codex child), which the leader sends to and waits on (#1238), and `formation_stop` and `formation_close` fence the Dispatch before the terminal is closed. A formation belongs to one PC (its orchestrator's), and a child is launched in `local` or in a saved environment of that PC's Orca (#1239): a Claude Code child of a saved environment is no Dispatch (`dispatchId` is null, `runId` is the leader's own Run), its terminal's command has that PC's `tsunagiai-mcp --child-plugin` write its plugin and settings (`remote_child_command`, `write_child_files`), and the launch sends it `HELLO` with `orchestration send --on {environment} --to {handle}` (`hello_args`), the leader reaching it the same way. `FormationEntry` and `FormationListChild` carry `awaitingPage` (#1151): whether a decision page of a child waits for the owner's reply (`formation_page::pending_pages`, from this PC's `pages.json`, or from `PulledEnv.pages` for a saved environment), which the list draws as 判断待ち. `formation_claude.md` is the `CLAUDE.md` of the orchestrator
- `formation_message.rs` (A-37, #1084, #1238): the messages between the leader and its children, which talk with Orca's orchestration (`orchestration send` and `check --wait`, run by the leader and the children themselves): `sync_orchestration` takes the messages of the formation's Run (`orchestration inbox`) and records who sent each, to whom, when and the first line in `formations/{name}/messages.jsonl` (no hook of Claude Code records them any more; a child's `--settings` file holds only the `permissions` for the Figma server, #1162), `formation_messages` reads it after taking them in (`read_synced`; a formation of a saved environment, through `messages.read` of the server, which takes in the Run of its own Orca the same way), and `formation_instructed` (#1087) gives the children that the leader told something and that have not answered yet, newest first, from the same record (`instructed`), for the compact view of the flow pane
- `formation_ask.rs` (A-37, #1105): the mark that the leader asked the owner a question (`formations/{name}/asked-owner.json`, written by the tool `formation_ask_owner`), the decision of `formation_list`'s `waiting` from the mark and the title of the leader's terminal (`judge`, `Seen`), and the clearing of the mark when the leader works again (a formation of a saved environment, through `asked.read` and `asked.clear` of the server)
- `formation_page.rs` (A-41): the decision pages: checks the input contract of a page (the kinds of card, the parts of a card, the facts, the images, the design items), holds its paths inside the repositories of the PC and their worktrees, resolves its evidence (`excerpt`, `diff` and `git-diff` as the rows of a side-by-side diff, `current` and `node`, #1157; `ts/formation-page-node.ts` draws a `node` as the deliverable draws it; the screen's right drawer and the links of its code names are `ts/formation-page-drawer.ts`, the top and bottom bars `ts/formation-page-bars.ts`, and the answers kept in the browser `ts/formation-page-store.ts`, #1158), and records it in `formations/{name}/pages.json`; the command `formation_page_image(name, child, root, path)` gives an image of the waiting page as a `data:` URI (#1153), and `formation_page_read` gives the page
- `formation_image.rs` (A-41, #1153; `orca_files.rs` also uses its `prepare` and `data_uri` for the image tab of A-18, #1088): the images of a decision page: the type by the extension, a file that is too large made smaller as a JPEG (a picture of too many pixels is refused from its header; the last 4 prepared images are kept), the `data:` URI, and the chunks in which `image.read` of the server sends an image of a saved environment
- `formation_reply.rs` (A-41): the reply of a decision page, pasted into the leader's terminal; `restore` reads the answers back from a page's `previous_reply` (#1156), and the reply carries the choice ビジネス側に確認する that a page with `hold` adds to its questions and the mark 仮置き of an answer (`PageAnswer.provisional`)
- `yomiyasu_gate.rs` (A-41): the yomiyasu gate of `formation_page`, which reads the records in `YOMIYASU_STATE_DIR` and does not check the `sample` text of an option, which is what the screen shows
- `formation_assets.rs` (A-41): the files of `src-tauri/formation/` and of `src-tauri/preview-plugin/` (A-45) that `build.rs` embeds: the leader's skill `feature-dev`, the children's plugin (`formation-plugin/` of the config folder: its skills and agents (`code-verifier`, `formal-verifier`, `figma-fetcher` and `design-prototyper` among them), `.mcp.json` that names the Figma server, the `permissions` for it that a child's `--settings` gets (`figma_permissions`: its read tools allowed and its write tools denied, #1162) and `skills/unit/scripts/formal-scope.py`, which the agents run with `python3 -I`), the preview plugin and the plugin `lsp` of `src-tauri/lsp-plugin/` (#1242)
- `formation_server.rs` (#890): the server mode of `tsunagiai-mcp` (`--serve`) on the PC of a saved environment, and `Client`, the app's connection to it, which reads an image of a page of that PC in chunks on one connection (`image.read`, `Client::image_read`, #1153; the server checks the page at the first chunk only and holds the last 4 images for the next ones). The pushes (#983): after `subscribe` the connection carries requests that the daemon pushes to the app (`Hub`, the daemon's end, and `Pushes`, the app's end), which the daemon takes from the `tsunagiai-mcp` of its PC on the unix socket `push.sock` of `remote/` (`push_to_daemon_result`), so the app's PC opens no port; the app's answer to a push is taken or refused, and a handler may give a value back with it (`result`, at most `MAX_RESULT` bytes, `None` for `preview.open`), which comes back through the socket to whoever pushed (#1244)
- `formation_remote.rs` (#891, #893): the app's side: puts `tsunagiai-mcp` in `remote/` of that PC from the GitHub Release, starts it, pins its key and version in `formation-remote.json` and connects to it. It also keeps one connection of pushes open to each saved environment that the owner agreed to (#983: `start_pushes` reads the saved environments at the start and every 30 seconds, `Subscriptions` ends the connection of one that left the list, and `keep_pushes` opens it again with a back-off; the requests taken are `preview.open` (A-45) and `lsp.settings`, `lsp.server_save` and `lsp.server_delete` (#1242, `lsp_answer`: the settings of the connection's environment, answered with the settings as saved; a save or delete needs a project in Orca's list of that environment, `LspPush::run` of `lsp_plugin.rs`), and every other push, `lsp.ssh_host_set` too, is refused with a reason). The app's secret key is in the keychain, service `jp.mysis.tsunagiai.formation`
- `preview_plugin.rs` (A-45, #986): the plugin of `src-tauri/preview-plugin/` (the skill that teaches Claude Code `preview_open`, and an `.mcp.json` made at the write) written into `preview-plugin/` of the config folder, by the app for its own PC and by `tsunagiai-mcp --preview-plugin` for the PC of a saved environment, its `.mcp.json` starting `tsunagiai-mcp --preview`; 「Claude を起動」 gives it to `claude` with `--plugin-dir` (`orca.rs`, `claude_command`; the first prompt of A-9 is a file of the worktree that the command reads and deletes, `orca_attach::drop_prompt`, never a word of the command line)
- `lsp_plugin.rs` (#1242, A-34): the plugin of `src-tauri/lsp-plugin/` (the skill that teaches Claude Code `lsp_settings`, `lsp_server_save` and `lsp_server_delete`, and an `.mcp.json` made at the write) written into `lsp-plugin/` of the config folder, by the app for its own PC (`--lsp-local`) and by `tsunagiai-mcp --lsp-plugin` for the PC of a saved environment (`--lsp`), and the three pushes (`lsp.settings`, `lsp.server_save`, `lsp.server_delete`) that the tools of `--lsp` send and the app reads (`LspPush`)
- `orca.rs` (A-6), with `orca_link.rs` and `orca_e2ee.rs` (the connection to Orca's runtime), `orca_handoff.rs` (A-9), `orca_attach.rs` (A-10, and A-47: the files dropped on the file pane, `orca_drop_taken`, `orca_drop_dir` and `orca_drop_file`), `orca_stream.rs` (A-12), `orca_pairing.rs` (the pairing of this machine's Orca, kept in the keychain, and the WebSocket to it, A-12), `orca_panes.rs` (A-17), `orca_popout.rs` (A-46: a tab of the work pane in a window `tab-{n}` of its own, the table of the windows in memory, the commands `orca_popout_*` and the close of such a window, which is left to the screen, or to the page of the window for a file, which holds its text and its save; a diff, a definition and a database tab are given to the window as conditions, and the window asks for a place of a definition and tells a lost connection through `orca_popout_place` and `orca_popout_lost`), `orca_files.rs` (the file pane and the editor, A-18, the download, A-22, the diff, A-24, the branches and the commits of a worktree, A-27), `orca_diff.rs` (A-24), `orca_language.rs` (A-21), `orca_icon.rs` (the icon of a file in the file pane, #965), `orca_preview.rs` (the HTTP server on `127.0.0.1` that serves the files of a worktree to the default browser, A-31, and the request that a Claude Code makes to open a preview tab, A-45: its checks, `OpenParams`, the two forms it is sent in, and `orca_preview_check`, the checks the app makes again when it takes the request, whose screen is the target `preview-open` of `ts/orca.ts`) and `orca_browse.rs` (the folders of a saved environment's server, for the picking dialog of A-38)
- `ghostty.rs` (Ghostty's settings for the Orca terminals, A-13), `orca_theme.rs` (the colors of the Orca terminals, A-14, with the table `orca_themes.json`), `orca_titles.rs` (the titles the owner gave to the sessions of the Orca list, A-8, in `orca-titles.json`)
- `ssh.rs` (this Mac's `ssh` command and the run of a process with a time limit, for `lsp.rs`, and the Host names of `~/.ssh/config` for the select of the ssh Host, #959)
- `lsp.rs` (A-34): how a language server is started for a worktree, and the settings of each repository (its servers, one for each language: language, name, command) in `lsp-settings.json`, and the start of the Claude Code tab that sets them up in the work pane, with its first instruction (`lsp_claude_start` with the plugin `lsp`, and `lsp_claude_prompt`, #976, #1247), with `lsp/detect.rs` (the table of the languages and their servers, and the finding of what a worktree has, #974, and the title and the icon of each language for the cards of the screen, #975), `lsp/server.rs` (the language server processes that stay, one for each worktree and language), `lsp/protocol.rs` (the LSP frame, messages and answers as pure functions), `lsp/container.rs`, `lsp/outside.rs` (#699), `lsp/view.rs` (#700) and `lsp/watch.rs`
- `database.rs` (the connection profiles of the database screen, #625), with `database/script.rs` (the script that opens the way to a connection before MySQL is logged in to, #718), `database/mysql.rs` (the MySQL session, D-2), `database/session.rs` (the sessions that stay open, and the databases and tables, D-3), `database/records.rs` (a page of the records of a table, D-4), `database/structure.rs` (the columns, engine and character set of a table, D-5) and `database/sql.rs` (the SQL of a query tab, D-6)
- `fonts.rs` (the fonts by screen, A-20), `side_menu.rs` (the order and the on and off of the six screens of the side menu, saved in `side-menu.json`, #676), `app_log.rs` (the app's log, A-28)

The modules shared by the services:

- `accounts.rs`: the list of accounts in `accounts.json`, and the atomic write of a settings file
- `auth.rs` (the OAuth login and the tokens), `keychain.rs` (the OS keychain, which every module reads, writes and deletes its secrets through; it moves the items of the old identifier on their first read, #750), `identity.rs` (the identifier, the config folder and the move of the old one, #750)
- `mail_address.rs` (splits a From or To header into a name and an address, and works out who a reply goes to, M-10), `mail_send.rs` (builds the message of a new mail or a reply and sends it, the command `send_mail`; the files of M-12 go into it as `multipart/mixed`), `mail_attach.rs` (M-12: whether a file may be attached, and the dialog that picks files)
- `images.rs` (the images in HTML mail, with `images/macos.rs`, which fetches an external image with NSURLSession) with `image_senders.rs` (the senders whose external images are shown without asking)
- `disk_cache.rs` (the kept copies of the last calendar weeks that the screen draws first at startup; the mail list is no longer kept, #739)
- `markdown_patch.rs` (puts an edit of the rich Markdown editor into the original text by lines, A-26; the mail of M-10 and the Slack posts of S-6 and S-21 also use it)
- `update.rs` (the self-update and its settings, U-1 and U-2)

## `tsunagiai-mcp`

It is `src/bin/tsunagiai-mcp.rs`; how to install it is in "Run" of the root `AGENTS.md`.
The tools are `list_inbox`, `get_thread`, `list_events` and `db_profiles` (read), `archive`, `set_read` and `trash` (write), `db_profile_save` and `db_test` (the connections of the database screen: save one with its script, and try it, D-8), and `lsp_settings` (read), `lsp_server_save`, `lsp_server_delete` and `lsp_repo_ssh_host_set` (write; the language servers of a project of the Orca screen, A-34, #960), and `screen_read` (read) and `screen_write` (write; the fields a screen holds, through the app's socket, A-36, #731) and `slack_thread_read` (read; no argument, the thread that the Slack thread screen has open, as data between `BEGIN` and `END` lines, through the target `slack-thread` of the app's socket, S-7, #735) and, for `screen_read` and `screen_write`, the target `mail-draft` (the fields `to`, `cc`, `bcc`, `subject` and `body` of a new mail, M-11, #490), and `skill_list` and `skill_get` (read) and `skill_save` (write; the skills of the settings' Skills tab with the functions of `skills.rs`, and then `changed` `skills` to the app, so that the tab fills its form again, A-32, #345), and `calendar_show_slots` (read; it only draws candidates of free time as red frames on the week of the calendar screen, through the target `calendar-slots` of the app's socket, and saves nothing, C-6, #1063), and `list_calendars` (read) and `calendar_set_shown`, `calendar_create_event`, `calendar_update_event` and `calendar_delete_event` (write; what the calendar screen does, with the functions of the app, and then `changed` `calendar` (`calendar-shown` for `calendar_set_shown`) to the app, so that it reads the week again, C-6, C-7, #1073; `list_events` also gives the detail of each event and its guests; an event that would invite a new guest is not sent: the tool writes the target `calendar-form` of the app's socket, which opens the form of the calendar screen with the values, and the owner saves it), and `todoist_projects` and `todoist_tasks` (read) and `todoist_add_task` (write; Todoist, with the token of the app's keychain entry, and it tells the Todo screen to read its list again, T-7, #732), and `preview_open` (the worktree's path and an `.html` file in it, checked as A-31 checks it (`orca_preview::check_open`), then asked of the app as a request to open the preview tab (A-45, #984): the push `preview.open` to the daemon of that PC through `push.sock` (`push_to_daemon_result`), and, when that fails, a write of the target `preview-open` of the app's socket; not marked `read_only_hint`, because the tab runs the page's scripts in a frame; offered with no argument and with `--preview`, not with `--formation` or `--calendar`).
Started with the arguments `--formation {name}` (the `mcp.json` of the orchestrator of that formation, A-37), it offers `formation_environments`, `formation_worktrees`, `formation_files`, `formation_read` and `formation_git` (they only read: the repositories of each environment, the worktrees of one, the entries of a folder, a file's text, and the git state and branches, #848), `formation_status` (`formation/status.rs`: it only reads how a launched child is doing, with its `orca worktree ps --agent-wait` state and the end of its terminal enclosed between `BEGIN` and `END` lines as data, A-41, #1100; the leader of `feature-dev` reads it in a patrol every 10 minutes, #1101), `formation_ask_owner` (`formation_ask.rs`, #1105: no argument; it writes the mark `formations/{name}/asked-owner.json` that the leader is about to ask the owner a question, and the list shows the leader as waiting for input only with that mark and a title of the leader's terminal that starts with `✳`; the app takes the mark away when the leader works again, and for a saved environment reads and clears it through `asked.read` and `asked.clear` of `--serve`), `formation_page` (`formation_page.rs`: a decision page that a child wrote, checked and recorded in `formations/{name}/pages.json`, A-41), `formation_plan`, `formation_launch` and `formation_close` (`formation.rs`: the children of that formation and their record `formations/{name}/children.json`, which these tools alone write, besides the names of closed children that the app takes out of it through `--serve`; they take `local`, the PC the orchestrator runs on, or a saved environment as a child's environment, #1239), `formation_stop` (`formation.rs`, #1132: it closes only the terminal of a child, when Orca's list says that it is the child's, and leaves its worktree, its branch and its entry of the record) and, of the tools above, only the reads (`list_inbox`, `get_thread`, `list_events` and `db_profiles`), because the orchestrator runs in auto mode and a write would run with no question; no other client is offered the formation tools, because `formation_launch` starts a Claude Code in auto mode.
Started with `--calendar` (the `mcp-calendar.json` of the calendar pane of A-36, which runs in the `auto` permission mode, C-6, #1074), it offers `list_events`, `list_calendars`, `calendar_set_shown`, `calendar_create_event`, `calendar_update_event`, `calendar_delete_event` and `calendar_show_slots` only (`CALENDAR_TOOLS`), because a write of any other tool would run with no question to the owner; it cannot be given with `--formation`.
Started with `--todo-draft` (the `mcp-todo-draft.json` of the pane of the page of a Todo's draft of A-36, which runs in the `auto` permission mode, S-18, #1148), it offers `screen_read` and `screen_write` only (`TODO_DRAFT_TOOLS`), both limited to the target `todo-draft` (`only_screen`), because a write of any other tool would run with no question to the owner and the draft is made from a Slack message that someone else wrote; it cannot be given with `--formation`, `--calendar` or `--preview`.
Started with `--preview` (the `.mcp.json` of the preview plugin of A-45, #986, which every Claude Code of 「Claude を起動」 and of A-9 gets, and A-9 can start it with the text of a mail or a message as its first prompt), it offers `preview_open` only (`PREVIEW_TOOLS`), because any other tool (a read of the mail, a trash, a post to Slack) would be one that an instruction hidden in that text could use; it cannot be given with `--formation` or `--calendar`.
Started with `--lsp-local` (the `.mcp.json` of the plugin `lsp` on the app's own PC, #1242), it offers `lsp_settings`, `lsp_server_save`, `lsp_server_delete` and `lsp_repo_ssh_host_set` only (`LSP_TOOLS` and `LSP_SSH_HOST_TOOL`), which read and write `lsp-settings.json` of this PC.
Started with `--lsp` (the same plugin on the PC of a saved environment), it offers the three tools `lsp_settings`, `lsp_server_save` and `lsp_server_delete` only, as tools of their own (`lsp_pushed_router`) that take `project` and no `environment` and push `lsp.settings`, `lsp.server_save` and `lsp.server_delete` to the app through `push.sock` (`push_to_daemon_result`), answering the settings the app gives back; they never fall back to this PC's file (a failure says that nothing was written here), and `lsp_repo_ssh_host_set` is not offered. Neither flag can be given with the other, `--calendar`, `--preview`, `--todo-draft` or `--formation`.
Started with `--formation-start {name}` (and `--project {repo}`, once for each project of the formation, none at all is fine: they are its first instruction, all in `local`, passed as `claude [prompt]`, so nothing is typed into its terminal afterwards, #882) instead, it serves nothing: it writes the files of that formation's orchestrator (`CLAUDE.md`, `mcp.json` that names this `tsunagiai-mcp` with `--formation {name}`, the launch script, an empty `.claude/settings.json` and the leader's skill `.claude/skills/feature-dev/`, written as the app writes them for its own pane) in `formations/{name}/` of this machine's config folder, and starts Claude Code there in place of itself, so an orchestrator can run on the machine of its children (#858); a failure is a line on stderr and a non-zero exit.
Started with `--child-plugin {formation} {name}` (the command of the terminal of a Claude Code child that a leader on another PC launches here, #1239) instead, it serves nothing: it writes `formation-plugin/` and `child-settings/{formation}-{name}.json` of this machine's config folder, prints the two paths on two lines and exits (a failure is a line on stderr and exit 1).
Started with `--lsp-plugin` (the command of the launch on the PC of a saved environment, #1242) instead, it serves nothing: it writes `lsp-plugin/` of this machine's config folder with itself as the server of the plugin's `.mcp.json` (`--lsp`), prints the folder's path on one line and exits (a failure is a line on stderr and exit 1).
Started with `--preview-plugin` (the command of 「Claude を起動」 on the PC of a saved environment, A-45, #986) instead, it serves nothing: it writes `preview-plugin/` of this machine's config folder with itself as the server of the plugin's `.mcp.json`, prints the folder's path on one line and exits (a failure is a line on stderr and exit 1).
Started with `--serve --bind {host}` (and `--client-key {key}`, the app's public key, which the app gives when it puts the program on the PC), it serves the records of the formations to the app (the children of `children.json`, the messages of `messages.jsonl` (#1084), the mark of a question of the leader (`asked.read` and `asked.clear`, #1105), the decision pages of `pages.json`, with its evidence resolved there the page of one child and the time it was recorded at, and the mark that its reply was sent, A-41): it makes its key pair in `remote/` of this machine's config folder, pins the app's key, starts the daemon (`--serve-run`) unless one of this version already runs and returns at once, printing one line, `TSUNAGIAI-SERVE {public key} {version}` or, for a failure, `TSUNAGIAI-SERVE-ERROR {reason}` (non-zero exit); `--serve-stop` ends the daemon (`TSUNAGIAI-SERVE-STOPPED`). It listens on `{host}:47823` only and serves no MCP (A-37, `requirements/constraints.md`, "Orca").
