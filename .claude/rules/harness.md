# The Claude Code harness

## Where things are

### Look in `.claude/` for what guards a change

Hooks are in `.claude/hooks/`, which is tracked, and they are wired in `.claude/settings.local.json`, which is not; worktrees use the main checkout's settings, so the hooks that run are the main checkout's.
`guard-public.sh` stops forbidden public words (`file` looks at the checkout the file belongs to, so a file of the worktree is checked there, and passes a file of another repository; `tree` and `log` look at the checkout of the directory they run in), `post-edit.sh` checks an edited file for forbidden public words (`guard-public.sh file`), runs rustfmt on an edited `src-tauri/**/*.rs`, runs `check-icons.sh` on an edited `ts/*.ts` or `src/index.html` (the shape of an icon is written only in `ts/icons.ts`, `frontend.md`; the checkout's own copy, skipped when it has none), and runs `tsc --noEmit` on the project (`ts` or `e2e`) of an edited `.ts` file under `ts/` or `e2e/`, or `wdio.conf.ts`, all in the checkout the edited file belongs to, not in `CLAUDE_PROJECT_DIR` (skipped when `node_modules` has no `tsc`, and for a file of another repository), `guard-e2e.sh` (the CI and E2E records) and `guard-review.sh` protect the records (`guard-review.sh` stops every call that names `record-review`, `.claude/reviews` or `/statuses/` unless it is release-verifier's, with two exceptions (#1375): one read-only command (`cat`, `head`, `grep`, `rg`, `sed -n` with line numbers only, `git diff`, `git show` or `git log`, run alone, with no `;`, `&`, `|`, `<`, `>`, newline, backtick, `$(` or `${`, and no `rg --pre`, `rg --hostname-bin` or `--output`), and a Write, Edit or MultiEdit of `record-review*.sh` or `guard-review.sh` under `.claude/worktrees/{name}/.claude/hooks/`, never of the main checkout's copy; running the scripts and writing `.claude/reviews/` stay stopped; `range-check.sh` is the one other writer of the pass record, and its command names neither, #932), and `pre-git.sh` checks the records of CI, E2E and review before a push (`run-ci.sh` and `run-e2e.sh` write the first two, and `check-records.sh` passes them with no record when the diff holds only files that no check reads, `testing.md`) for the HEAD of the checkout the command runs in (the `cwd` of the hook input, moved by a leading `cd DIR &&` or `cd DIR;` and by the place of `git -C`), not of `CLAUDE_PROJECT_DIR`, while the records are read from the main checkout, and runs `check-guard-e2e.sh` when the pushed range touches `guard-e2e.sh`, `hook-log.sh` or that script, `check-pre-git.sh` when it touches `pre-git.sh`, `hook-log.sh`, that script, `check-ci.sh`, `check-e2e.sh`, `check-records.sh` or `release-only-diff.sh`, `check-range-check.sh` when it touches `range-check.sh`, `record-review.sh`, that script, `check-ci.sh`, `check-e2e.sh`, `check-records.sh` or `release-only-diff.sh`, and `plan-release-test.py` when it touches `plan-release*.py`, `use-worktree.sh`, `ensure-deps.sh` or `post-gh.sh` (`testing.md`). Every hook that `settings.local.json` wires (`guard-e2e.sh`, `guard-review.sh`, `post-edit.sh`, `post-gh.sh`, `pre-git.sh`, `session-start.sh`) sources `hook-log.sh` and, once it knows the run is its business (a call that ends early with exit 0 is not logged, and reads no clock), appends at its exit its name, start time, duration and exit code to `logs/hooks-{YYYY-MM-DD}.log` of the main checkout (`logs/` is gitignored; #260), and `pre-git.sh` adds one line for each `gate` with its name, duration and exit code, so that a slow hook can be traced afterwards. The log holds no command, path or file content, and a log that cannot be written changes neither the hook's decision nor its exit code. `TSUNAGIAI_HOOK_LOG_DIR` replaces the directory, and the self-tests set it to a temporary one. `session-start.sh` starts `clean-target.sh` in the background (detached, output dropped, so the session does not wait) and runs `ensure-deps.sh`, which runs `npm ci` when `node_modules` is missing or was installed from another `package-lock.json` than the checkout's (`run-ci.sh`, `run-e2e.sh` and `use-worktree.sh` call it too; #1017), and `post-gh.sh` tells the session to go on with steps 1 to 4 of `issue-plan` after `gh issue create`, and after `gh pr merge` waits (up to 30 seconds, `TSUNAGIAI_CLOSE_WAIT`) until the issues that the merged pull request closes (`closingIssuesReferences`, of the pull request that the command finds from the `cwd` of the hook input, moved by a leading `cd DIR &&` or `cd DIR;` as in `pre-git.sh`, when the command names none) are closed, because GitHub closes them a few seconds after the merge, then runs `plan-release.py release` and, when it succeeds, tells the session to launch `release-watcher` for a `follow_up` or a `tag_due` (the lead tags by hand only when it returns `no-run`), and `release-preparer` when changes wait, then `release-watcher` once the Release PR has merged (`.claude/skills/release/SKILL.md`, the lead's steps).
`.claude/skills/` holds `improvement-proposal` (a session only: file refactoring and harness improvements, and UI/UX ones, as issues), `issue-plan` (an issue, made once it is verified, designed and checked on a real machine where it needs one, and its spec is decided and shown when it carries a decision of the owner, and the parent issue of a feature), `implement` (propose the open issues, ranked, and implement the ones the owner names on one branch with one pull request, then fix up to three items of the issues of left review Lows, flaky tests and retrospectives, prepare the Release PR, merge it, see the release through, look back on the run and give the worktrees back; `/implement`, 「#N を実装して」 and 「次を進めて」, which only proposes), `release` (prepare the Release PR, merge it, and see the release through: the tag, the release run and the comments on the issues, by launching `release-preparer` and `release-watcher`; step 7 of `implement`, and the session that `post-gh.sh` tells), `retrospective` (look back on a run, and file one 「振り返り:」 issue for each cause in the skills and subagents; step 8 of `implement`, and `/retrospective`) and `readme-product` (the README as a product page, and its photos).
`.claude/agents/` holds the reviewers (`code-reviewer`, `performance-reviewer`, `security-reviewer`), `release-verifier`, `release-preparer` (Sonnet: Procedure A of `release`) and `release-watcher` (Haiku: Procedure B of `release`; #1258), `issue-ranker`, and the three scouts of `improvement-proposal`, `ux-scout`, `refactor-scout` and `harness-scout`.
No scheduled run is left: `clean-target.sh` runs from `session-start.sh` (below), and no launchd job is used (at the owner's instruction, 2026-11-23; #1330). The X post that ran at 00:30 is removed (at the owner's instruction, 2026-11-23), and the job at 22:00 that ran `improvement-proposal` is retired (#485).
`dependabot-issues.sh` makes an issue for each open Dependabot pull request that has none (`implement` skill, "Rules"; `DEPENDABOT_ISSUES_DRY_RUN=1` prints without making), and `use-worktree.sh` makes the worktree of a branch and, with `--park`, removes it (`worktree.md`).
`range-check.sh {passed HEAD} {list file}` checks a fix that holds only the non-blocking findings of an already merged version (`range-check.sh origin/main {list file}`), in a session, with no release-verifier launch (#932; a pass of a branch is not followed by such a fix, #1012; its normal route is step 6 of `implement`, #1211): the tree is clean, the passed commit has a pass record or is `origin/main` or its ancestor (a commit of main passed this gate when it entered main), and is an ancestor of HEAD, `check-records.sh` passes on HEAD (its CI and E2E records, or a diff from the passed commit of files that no check reads only), and every changed path appears in the list of the fixed findings (each line holds a `path` or `path:line`); when all hold it writes HEAD's pass record through `record-review.sh`, otherwise it prints the reason or the paths outside the list and exits 1 (`review.md`). `check-range-check.sh` is its self-test, on a temporary repository and temporary records.
`plan-release.py` prints `next --mine` (`start` is the queue in the basic order of "Order the issues" in `issues.md`, the Dependabot issues first), `release` (what waits for the merge of the Release PR, not counting the issues that the last Release PR closed (its `Closes`); the Release PR, the version it writes in `CHANGELOG.md`, `urgent`, and `tag_due`, the tag of a merged Release PR that does not exist yet: `release.yml` makes it at the merge, so `tag_due` shows only until it has, or when the workflow did not, and `follow_up`, the merged Release PR whose tag exists and whose issues are not yet commented, until the agent that did so marks it, `.claude/skills/release/SKILL.md`) and `close` (closes the parents whose sub-issues are all released), and `split {file}` (the split of `issue-plan` step 3: it checks everything, then makes the parts as sub-issues of the large issue, with their comments, with `gh` as an argument list, and comments their numbers on the large issue, which stays open as their parent; with no parts it only labels the issue `whole`; `issue-plan` skill, "Rules").
`plan-release.py snapshot` closes the open issues of other authors as not planned, before it prints the issues in the basic order for `issue-ranker` (`issues.md`, "Trust only the owner's issues and comments"), and refuses an open issue of the owner that has no `point:*` label. No order is saved.
`plan-release.py claim --worktree {path} {n}...` claims issues for a worktree (`.claude/claims/{n}/owner` of the main checkout, gitignored with the rest of `.claude/`), and `next` lists the issues that a worktree which still exists has claimed in `claimed`, outside `start` (`worktree.md`, "Claim an issue before you start it"; #1008).
`clean-target.sh` keeps `src-tauri/target` from growing with the old output of the app itself, and runs with no argument, in the background, from `session-start.sh` at the start of every session (#1330); before each worktree and before each deletion it checks for `cargo` or `rustc`, and when one runs it logs one line and ends with the rest kept, and a second run does the same as the first. What it deletes is in the comment at the top of the script.
A gate that stops a command is a finding about the change, not an obstacle to route around.

```text
Good: pre-git.sh refuses the push -> read its message, and fix what it names
Bad:  pre-git.sh refuses the push -> write the record by hand
```

### Build graphify only in the main checkout, after the merge

`graphify-out/` is gitignored, so a graph built in a worktree is lost with it, and a branch's graph does not describe main.

```text
Good: merge -> fast-forward the main checkout -> update the graph there
Bad:  build the graph in a worktree and delete the worktree
```

### Write the agents and the rules in English

`.claude/agents/` and `.claude/rules/` are written in English (at the owner's instruction, 2026-11-18; #953). `.claude/agents/`, `.claude/evals/`, `.claude/hooks/`, `.claude/rules/`, `.claude/skills/` and `.claude/tools/` are tracked and edited on a worktree branch, and the rest of `.claude/`, with the two gitignored rules and `.claude/hooks/public-words`, is edited in the main checkout (`worktree.md`).
The hooks and the gates run the main checkout's copy of `.claude/hooks/` and `.claude/tools/`, so a change to either takes effect after the merge and the fast-forward of the main checkout.

```text
Good: change .claude/rules/review.md on the branch, and .claude/rules/machines.md in the main checkout
Bad:  change .claude/rules/machines.md in the worktree
```

## Changing the skills and the subagents

### Slim a skill or a subagent, and check each change with a small eval

A change to this project's skills (`.claude/skills/`) and subagents (`.claude/agents/`) aims at slimming them: cut or merge before adding, and give the line count of each changed definition before and after in the pull request (at the owner's instruction, 2026-11-21; #1213).
Every change to one of them comes with a small eval, `.claude/evals/{name of the skill or subagent}.json`, in the form of skill-creator: `skill_name` and `evals`, 1 to 3 cases, each with `id`, `name`, `prompt`, `files`, `expected_output` and `assertions`, at least one of them on the changed behavior. Its fixtures are under `.claude/evals/files/{name}/`.
The eval runs in the session: for each case one subagent acts by the definition on the case's files and writes nothing to GitHub (it writes the command it would run instead), and another subagent grades that result against the assertions. Every case passes before the commit, and the result goes in the body of the pull request. Never `claude -p`.
The global skills and subagents (`~/.claude/`, kept in another repository) are out of scope.

```text
Good: a step of `implement` is fixed by merging two sentences -> "117 -> 115 lines" in the pull request -> a case of `.claude/evals/implement.json` covers the step -> one subagent acts, another grades -> all pass -> commit
Bad:  a paragraph is added to a skill with no try at cutting, and committed with no eval
Bad:  the eval runs with `claude -p`, or the subagent that acted grades itself
```
